## 1. 데이터 흐름

```
┌─ 소스 : "원시 데이터를 얻는 방법"만 다르다 ────────────────┐
│  우리은행·우체국   →  웹에서 xls 다운로드                   │
│  카드 명세         →  웹에서 엑셀 다운로드                   │
│  네이버페이·쿠팡   →  오빠두 템플릿(쿠키) → xlsx            │
│  현금·기타         →  손입력                                │
└──────────────────────────┬─────────────────────────────────┘
                           ↓ 파일 업로드
                  ┌─────────────────┐
                  │   기관별 파서    │  ← 소스마다 함수 1개. 나머지는 전부 공통
                  └────────┬────────┘
                           ↓
      거래 후보 { 날짜, 금액, 원본가맹점명, 상세명?, 사업자번호?,
                 승인번호?, 계좌, 거래후잔액? }
                           ↓
                  ┌─────────────────┐
                  │   중복 감지      │  승인번호 우선 → 없으면 조합지문
                  └────────┬────────┘
                           ↓ 신규 건만
      ╔══════════════════════════════════════════════════╗
      ║              분 류 엔 진 (4계층)                  ║
      ║  ① 상품명 완전일치(이력)   커버 45% · 정확 97%    ║
      ║  ② 사업자번호 정확매칭     카드·은행 소스          ║
      ║  ③ 키워드 규칙            일부                    ║
      ║  ④ LLM 추론               나머지 ~50%             ║
      ╚════════════════════┬═════════════════════════════╝
                           ↓
              분류 제안 + 신뢰도 + 판단 근거
                           ↓
      ┌────────────────────────────────────────────────┐
      │  ★ 확인 화면 — 사람이 개입하는 유일한 지점        │
      │    신뢰도 높음 + 소액 → 자동 확정 (훑기용 표시)   │
      │    신뢰도 낮음 or 고액 → 확인 요청               │
      └────────────────────┬───────────────────────────┘
                           ↓ 확정
                        [ 저장 ]
                           ↓
              거래후잔액 대조 → 누락·중복 경고
```

**핵심 성질**: 소스가 늘어도 **파서 함수 하나**만 추가된다. 중복감지·분류·확인·저장·검증은 전부 공통이다. (v1 `importer.py`의 `PARSERS` 레지스트리가 이미 이 구조)

## 2. 사용자 흐름 — 세 가지 진입 동기

```
① 정리하러 왔다 (월 1~2회)
   파일 업로드 → "200건 들어왔습니다"
                  ├ 자동 분류됨      ← 쭉 훑으며 스캔
                  └ 확인 필요 N건    ← 하나씩 판단
   → 확정
   ★ 자각 지점 1 : 최근 소비를 눈으로 지나감

② 이번달/지난달 얼마 썼나 (목적 있는 확인)
   월 요약 → 분류별 비중 → 궁금한 분류 클릭 → 그 안의 내역
   ★ 자각 지점 2 : "식비가 왜 이래?" → 상세까지 파고듦

③ 심심해서 들여다본다 (탐색)
   기간·분류·가맹점 필터 / 추이 / 지난달 대비
   ★ 자각 지점 3 : 우연한 발견
```

### 설계 원칙 P-1 (자각 보존)

> **자동화는 자각을 대체하지 않고, 자각을 위한 여유를 만든다.**
> 분류 결과는 **제안**으로 제시하고 사람이 훑는 흐름을 유지한다.
> **사용자가 아무것도 보지 않아도 되는 설계는 목적 위반이다.**

### v1의 구멍

| 확인 방식 | v1 | 필요성 |
|---|---|---|
| **통계로 본다** (요약 → 드릴다운) | ✅ 대시보드·분석 6화면 | 규모 파악 |
| **내역을 쭉 훑는다** (스캔) | ❌ **없음** | **"이건 필요 없었네"가 나오는 곳** |

`식비 32만원`을 봐서는 자각이 안 생기고 `티코다크 38,800원`을 봐야 생긴다.
→ **훑기 화면이 중심 화면**이며, 통계는 그 입구다.

### ①과 ②는 같은 컴포넌트다

정리하며 훑는 행위 = 회고하며 훑는 행위. **분류 확인 화면이 곧 회고 화면**이다.
진입 맥락과 대상 기간만 다르므로, 같은 컴포넌트를 두 맥락에서 재사용한다.

## 3. 도메인 모델

### 3-1. `transactions` (거래)

| 컬럼 | 용도 | 출처 |
|---|---|---|
| `date`, `amount`, `type` | 기본 | — |
| **`account_id`** | 어느 계좌·카드에서 | **신설** |
| `raw_merchant` | 원본 가맹점명 (추적성) | v1 보유 |
| **`item_name`** | **세부 내용** — 상품명 or 항목명 (`파래도식락김`, `관리비`) | **신설** |
| `category_id` | 분류 | v1 보유 |
| **`biz_no`** | 사업자번호 (분류 키) | **신설** |
| `external_ref` | **승인번호** (중복 자연키) | v1 컬럼 재활용 |
| **`bearer`** | 자금 주체 (`self`/`child`/`shared`) | **신설** |
| **`balance_after`** | 거래후잔액 (정합성 검증) | **신설** |
| `source` | manual/bank/card/oppadu | v1 보유 |
| `memo` | 자유 메모 | v1 보유 |

> **`item_name`은 컬럼 하나다.** 별도 `items` 테이블(1:N)은 만들지 않는다 → [ADR-002](adr/ADR-002-품목은-컬럼으로.md)

### 3-2. `accounts` (신설)

`id, user_id, institution(우리은행/우체국/카드사), name, type(입출금/예금/카드/현금/간편결제), is_active`

### 3-3. `categories` (v1 확장)

| 변경 | 이유 |
|---|---|
| `+ code` | 11자리 표시용 코드. **12년치 데이터의 조인 키** |
| `+ kind` | `consumption`/`saving`/`investment`/`transfer` — **`kinds.py` 하드코딩 제거** → [ADR-003](adr/ADR-003-분류판정을-데이터로.md) |
| `+ is_active` | 실사용 132개만 활성, 미사용 170개는 보존하되 비활성 |
| `parent_id` (기존) | 깊이 제한 없음 → 5단계 그대로 수용 |

### 3-4. `merchant_rules` (v1 확장)

`+ biz_no`(사업자번호 정확매칭) `+ item_name`(상품명 완전일치) `+ confidence` `+ match_type`

## 4. 분류 엔진

### 4-1. 실측 근거

22,047건 전수 분석 결과:

| 측정 | 값 | 의미 |
|---|---|---|
| **이력 기반 커버율** (2019~ 누적) | **44.8%** | 매년 55~65%가 **처음 보는 상품명** |
| **상품명 → 분류 일관성** | **96.9%** | 이력이 있으면 거의 확실 |
| 분류가 갈리는 상품명 | 8,521개 중 339개 (4.0%) | 예외는 드묾 |

**결론: 이력만으로는 45%가 상한이다.** 아빠의 실제 매칭률 32%도 같은 계열의 숫자다 — **더 열심히 해서 해결될 문제가 아니라 구조적 상한이었다.**
→ **LLM은 선택이 아니라 목표(85%) 달성의 필수 조건.**

### 4-2. 계층 구조

| 계층 | 방식 | 커버 | 정확도 | 비용 |
|---|---|---|---|---|
| ① | 상품명 완전일치 (이력) | 45% | 97% | 0 |
| ② | 사업자번호 정확매칭 | 카드·은행 | 최상 | 0 |
| ③ | 키워드 규칙 | 일부 | 중 | 0 |
| ④ | **LLM 추론** | 나머지 ~50% | 실측 예정 | ★ |

상위 계층이 맞히면 하위는 호출하지 않는다. **LLM 호출량은 월 80~100건 수준.**

### 4-3. 자동확정 정책

[02-A 3절](02-A_요구사항_추출.md)의 파레토 역전(상위 30개 = 건수 90%/금액 19%, 롱테일 = 건수 10%/금액 81%)에 근거한다:

```
신뢰도 높음 + 소액   →  자동 확정 (훑기 목록에는 표시 — P-1)
신뢰도 낮음 or 고액  →  확인 요청
```

**오분류 비용이 큰 쪽(고액 롱테일)에 사람을 배치한다.**

### 4-4. 부수 효과 — 마이그레이션이 곧 학습이다

아빠의 **8,521개 `상품명 → 분류` 매핑**을 규칙으로 씨딩하면 **첫날부터 45% 자동 분류**된다. 아빠 현재 수준(32%)을 시작부터 넘는다.

그리고 **22,047건이 정답 라벨이 붙은 평가셋**이다:
- 과거 데이터로 규칙·프롬프트 구성 → 2026년 데이터로 정확도 검증
- **Step 7(TDD)에서 "분류 정확도 N% 이상"을 실제 테스트로 걸 수 있다**
- 감이 아니라 숫자로 개선을 증명한다

## 6. 인터페이스 목록

```
Parser            parse(filename, content) -> list[거래후보]
                  구현체: 우리은행, 우체국, 카드사, 오빠두(네이버/쿠팡), 수동

Deduplicator      is_duplicate(후보) -> bool
                  승인번호 우선, 조합지문 폴백

Classifier        classify(후보) -> (category_id, confidence, reason)
                  구현체: History / BizNo / Keyword / LLM
                  LLM 하위 구현체: Ollama / API      ← 실측으로 확정

ConfirmPolicy     needs_review(제안, 금액) -> bool
                  신뢰도·금액 임계

Reconciler        verify(계좌, 기간) -> 불일치 목록
                  거래후잔액 대조
```
