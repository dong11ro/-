# ADR-011: 복구 경로를 이중화한다 — DB 백업 + 원본 파일 재파싱

- **상태**: 채택
- **날짜**: 2026-08-31
- **관련**: NFR-01, FR-04, R-3, 위협 L-1/L-2

## 맥락

위협모델(STRIDE+**L**) 결과 **상위 2개가 모두 유실(Loss)** 이었다:

| 순위 | 위협 | 가능성 | 영향 |
|---|---|---|---|
| 1 | **L-1** 디스크 고장 → 12년치 전손 | 중 | **치명** |
| 2 | **L-2** 마이그레이션 재실행·오류로 훼손 | **높음** | 높음 |

전통적 보안 위협(위장·권한상승·부인)은 하위였다. **우리 시스템의 적은 공격자가 아니라 고장과 실수다.**

그리고 [R-3](../01_제품비전.md)에 적어둔 대로 *"데이터 유실 = 신뢰 상실 = 즉시 이탈"* 이므로, 아빠가 12년치를 맡기는 순간 이것이 프로젝트 최대 리스크가 된다.

## 발견 — v1은 업로드 원본을 저장하지 않는다

```python
# backend/app/main.py
content = await file.read()      # 메모리에서 파싱하고 버림
```

원본이 없으면 **DB가 손상됐을 때 재구성할 방법이 없다.** FR-04(원본 파일 보관)를 `Should`로 뒀는데, 복구 관점에서 보면 등급이 다르다.

## 결정

**복구 경로를 두 겹으로 만든다. 서로 다른 실패를 막는다.**

| 계층 | 무엇을 보존 | 무엇을 복구 | 어떤 실패를 막나 |
|---|---|---|---|
| **① DB 덤프** (`pg_dump -Fc`) | 전체 상태 (사람이 수정한 분류 포함) | 그 시점 전부 | 디스크 고장, 컨테이너 소실 |
| **② 원본 파일 보관** | 업로드된 은행·카드 파일 원본 | **재파싱으로 거래 재구성** | 덤프 손상·누락, 파서 버그 소급 수정 |

**②가 있으면 RPO가 사실상 0이 된다.** 마지막 백업 이후 업로드분도 파일이 남아 있으면 다시 넣을 수 있다.
→ **FR-04를 `Should` → `Must`로 승격한다.**

### 백업 시점 — 서버가 상시 가동이 아니다

cron 야간 백업은 서버가 꺼져 있으면 돌지 않는다. 따라서 **시간이 아니라 사건에 건다**:

```
① 업로드 확정 직후        ← 데이터가 변하는 시점
② 마이그레이션 실행 전     ← L-2 방어. 백업 없이는 실행 자체를 막는다
③ 앱 기동 시 (마지막 백업이 7일 이상 지났으면)
```

### 보관 위치

같은 디스크에 두면 L-1을 못 막는다. **최소 두 곳**:

| 위치 | 목적 |
|---|---|
| 서버 로컬 (`backups/`) | 빠른 복구 |
| **다른 물리 매체** (외장/아빠 PC) | 디스크 고장 대비 |

외부(클라우드) 보관 시 **암호화 필수** — 백업본은 평문 금융데이터 덩어리다 (위협 I-2).

## 검증 — 실제로 돌렸다 (2026-08-31)

문서상 주장이 아니라 실행 증빙을 남긴다. 격리 컨테이너에서 실제 규모(22,047건)로 리허설했다.

| 항목 | 실측 |
|---|---|
| `pg_dump -Fc` | **0.22초 / 1.3MB** |
| `pg_restore` | **0.33초** |
| 재해 시뮬레이션 | 컨테이너+볼륨 **완전 삭제** → 신규 기동 → 복구 |
| 결과 | **체크섬 8종(md5 digest 포함) 완전 일치 — PASS** |
| 복구 객체 | 4 테이블 / 7 인덱스 / 4 FK |

**RTO 근거**: 22,047건 복구에 1초 미만. 12년치가 10배로 늘어도 수 초다.
→ 현실적 RTO는 복구 시간이 아니라 **사람이 알아차리고 조치하는 시간**이 지배한다.

### 검증 중 발견한 결함

```
ERROR: there is no unique or exclusion constraint matching the ON CONFLICT specification
```

`external_ref`에 **부분 유니크 인덱스**(`WHERE external_ref IS NOT NULL`)를 걸었더니 `ON CONFLICT (external_ref)`가 매칭되지 않았다. 조건을 명시해야 한다:

```sql
ON CONFLICT (external_ref) WHERE external_ref IS NOT NULL DO NOTHING
```

**FR-28(멱등성)을 "설계했다"로 끝냈으면 런타임에 터졌을 결함이다.**
→ 교훈: **멱등성은 선언이 아니라 실행으로 확인한다.** Step 7 테스트에 고정한다.

## 결과

- ✅ 위협 1·2위에 실측 근거를 갖춘 방어책
- ✅ RPO ≈ 0 (원본 파일 + 덤프)
- ✅ 백업·복구가 **1초 미만**임을 확인 → 자동 백업의 성능 부담 없음
- ✅ 부분 인덱스 + ON CONFLICT 함정을 사전 발견
- ⚠️ **FR-04 승격에 따라 파일 스토리지가 Must가 됨** (용량 관리 필요)
- ⚠️ 외부 보관 시 암호화 미구현이면 I-2가 남는다

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| **DB 덤프만** | 덤프가 손상되거나 백업 사이에 유실되면 복구 불가. 파서 버그를 소급 수정할 수도 없다 |
| **원본 파일만** | 사람이 수정한 분류·규칙이 재현되지 않는다 |
| **볼륨 스냅샷** | Docker 볼륨은 파일 복사로 정합성이 깨질 수 있다. `pg_dump`가 정석 |
| **cron 야간 백업** | 서버가 상시 가동이 아니라 실행이 보장되지 않는다 |
