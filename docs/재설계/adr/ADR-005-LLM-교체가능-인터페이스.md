# ADR-005: LLM을 교체 가능한 인터페이스 뒤에 두고 실측으로 정한다

- **상태**: 채택
- **날짜**: 2026-08-29
- **관련**: RQ-09, NSM

## 맥락

22,047건 전수 분석 결과:

| 측정 | 값 |
|---|---|
| 이력(상품명 완전일치) 기반 커버율 | **44.8%** — 매년 55~65%가 처음 보는 상품명 |
| 상품명 → 분류 일관성 | **96.9%** |

**이력·규칙만으로는 45%가 구조적 상한**이며 목표(자동 분류율 85%)에 도달할 수 없다.
아빠의 실제 매칭률 32%도 같은 계열의 숫자다 — 더 열심히 해서 해결될 문제가 아니었다.

→ **LLM은 선택이 아니라 필수 조건이다.**

## 실행 조건

| 조건 | 값 |
|---|---|
| 입력 | 상품명 + 가맹점명 (짧은 텍스트) |
| 출력 | 132개 분류 중 하나 |
| 볼륨 | **월 80~100건** |
| 지연 허용 | 배치, 수 분 OK |
| 민감도 | **아빠의 소비 내역** ★ |

볼륨·지연은 로컬이든 API든 여유롭게 충족한다. 실제 판단 기준은 **프라이버시 vs 한국어 상품명 이해 정확도** 둘뿐이며, **둘 다 지금은 알 수 없다.**

## 결정

`Classifier` 인터페이스 뒤에 두고, **정답셋으로 실측한 뒤 확정**한다.

```
Classifier.classify(후보) -> (category_id, confidence, reason)
  ├ HistoryClassifier   상품명 완전일치
  ├ BizNoClassifier     사업자번호
  ├ KeywordClassifier   규칙
  └ LLMClassifier       ├ OllamaBackend   (로컬, RTX 3060 12GB)
                        └ ApiBackend      (외부)
```

## 근거

**우리에겐 22,047건의 정답 라벨이 있다.** 과거 데이터로 규칙·프롬프트를 구성하고 2026년 데이터로 검증하면, **감이 아니라 숫자로** 백엔드를 고를 수 있다. 이런 조건에서 미리 정하는 것은 근거 없는 추측이다.

실험은 **본인(P1) 데이터로만** 수행해 아빠 데이터의 외부 전송을 피한다.

## 결과

- ✅ 정확도·비용·프라이버시를 실측 비교 후 결정
- ✅ Step 7에서 **"분류 정확도 N% 이상"을 실제 테스트로 강제**할 수 있다
- ✅ 나중에 모델을 바꿔도 호출부가 안 바뀐다
- ⚠️ 초기에 백엔드 2개를 만드는 비용 — 다만 인터페이스가 얇아 부담이 작다
- ⚠️ 로컬 채택 시 GPU가 있는 Windows 서버에 종속되며 Mac 개발환경과 불일치

## 기각한 대안

- **로컬 확정** / **API 확정** — 둘 다 정확도를 모르는 상태의 추측이다. 평가셋이 있는데 실측하지 않을 이유가 없다.
