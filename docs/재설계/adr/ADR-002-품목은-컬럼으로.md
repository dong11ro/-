# ADR-002: 품목을 별도 테이블이 아닌 컬럼으로 둔다

- **상태**: 채택
- **날짜**: 2026-08-29
- **관련**: RQ-12, RQ-14

## 맥락

아빠 목적(*"이건 필요 없었네"* 자각)을 달성하려면 `마트 50,000원`이 아니라 `티코다크 38,800원`처럼 **세부 내용이 보여야** 한다. 이를 근거로 `거래 1 : 품목 N` 스키마를 Must로 승격했었다.

그러나 다시 따져보니 **MVP에서 1:N이 실제로 쓰일 곳이 없었다.**

| 소스 | 한 거래의 품목 수 |
|---|---|
| 은행·카드 | 0개 (가맹점만) |
| 반복 항목(주거비·통신비) | 1개 |
| 쿠팡·네이버(오빠두) | 상품마다 1행으로 들어옴 |
| 마트 영수증 | N개 — **그런데 MVP에서 제외하기로 함** |

1:N이 필요한 유일한 근거(영수증)를 스스로 MVP에서 뺀 뒤에도 테이블은 남기려 했다. 앞뒤가 맞지 않았다.

## 결정

`transactions.item_name` **컬럼 하나**를 둔다. 값이 없으면 비운다.
별도 `items` 테이블은 **영수증 OCR을 실제로 구현할 때** 도입한다.

## 근거

1. **YAGNI.** 프로젝트 원칙: *"No abstractions for single-use code. No flexibility that wasn't requested."*
2. **양방향 문이다.** `1:1 → 1:N` 전환은 각 행이 거래1+품목1이 되는 기계적 변환이라 쉽다. 반대 방향이 어렵다. **쉬운 방향이 나중에 필요한 쪽**이므로 지금 결정할 이유가 없다.
   - 초안에서 이를 "단방향 문"이라 판단했으나 **틀렸다.**
3. **아빠 원장도 실제로 1:1이다.** `지출` 시트는 한 품목이 한 행이고, "이 10줄이 한 결제"라는 연결 자체가 없다. 22,047건이 그대로 1:1로 이관된다.

## 결과

- ✅ 테이블 하나와 전용 UI 하나가 사라졌다
- ✅ 목적(자각)은 그대로 달성 — 화면에 `item_name`을 보여주면 된다
- ⚠️ 영수증 OCR 도입 시 마이그레이션 1회 필요 (기계적)
- ⚠️ 품목합과 거래액을 대조하는 검증은 그때까지 불가

## 기각한 대안

- **거래 1:N 품목 테이블** — MVP에 사용처가 없다. 과잉 설계.
- **품목 개념 자체를 배제** — 쿠팡·네이버에서 **비용 0으로 들어오는 상품명**을 버리게 된다.
