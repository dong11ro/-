# ADR-012: 감염을 전제하고 방어한다 — 백업 암호화·오프사이트·로컬 노출 최소화

- **상태**: 채택
- **날짜**: 2026-08-31
- **관련**: 위협 M-1/M-2/L-1/I-2, NFR-01/03/06, [ADR-011](ADR-011-복구-이중화.md)

## 맥락 — 위협모델의 구멍

[07_보안_NFR](../07_보안_NFR.md) 초판은 *"외부 공격자는 접근 경로가 없다(내부망 전용)"* 를 전제했다. **틀렸다.**

**PC가 감염되면 공격자가 내부망 안에 생긴다.** 감염 경로는 방화벽과 무관하다 — 이메일 첨부, 다운로드, USB, 취약한 소프트웨어. 그리고 실제 취약점이 이미 존재한다:

```yaml
# docker-compose.yml
POSTGRES_PASSWORD: ledger      # 계정명과 동일한 약한 비밀번호
ports:
  - "5432:5432"                # 호스트 전체(0.0.0.0)에 바인딩
```

감염된 PC(또는 같은 내부망의 다른 기기)에서 `psql -h <서버> -U ledger`만으로 **12년치 금융데이터에 접근**된다. 인증 없는 API보다 이 경로가 더 직접적이다.

**그리고 랜섬웨어는 더 나쁘다**: DB와 백업이 **같은 디스크에 있으면 함께 암호화**되어 L-1(전손)과 동일한 결과가 된다.

## 먼저 정리 — 암호화는 위협별로 효과가 다르다

*"도커 볼륨을 암호화하면 되지 않나"* 라는 접근을 검토했고, **감염에는 효과가 없다**는 결론이다.

| 위협 | 디스크/볼륨 암호화 | **백업 암호화** |
|---|---|---|
| 디스크 도난 · PC 폐기 | ✅ 유효 | ✅ |
| **악성코드 감염 (가동 중)** | ❌ **무용** | ⭕ 백업은 보호 |
| **랜섬웨어** | ❌ **무용** | ⭕ 오프라인/불변이면 |
| 클라우드 업로드 유출 | — | ✅ 유효 |

**이유**: 시스템이 켜져 있으면 볼륨은 **이미 복호화된 상태로 마운트**되어 있다. 악성코드는 그냥 읽으면 된다. 저장 시 암호화는 *"꺼진 디스크"* 를 지키는 기술이다.

→ **볼륨 암호화보다 백업 암호화가 압도적으로 가치 있다.** 백업은 실제로 밖으로 나가고(클라우드) 오프라인으로 보관된다.
→ 디스크 암호화가 무의미하진 않다(PC 폐기·매각 시 유효). 다만 **OS 기본 기능(BitLocker/FileVault)으로 충분**하며 도커 볼륨을 따로 암호화할 이유는 없다.

## 결정

### 1. 백업은 3-2-1 규칙을 따르고, 오프사이트 사본은 암호화한다

```
3벌  원본 + 백업 2개
2개  서로 다른 매체
1개  오프사이트

  원본    서버 PC 볼륨
  백업1   서버 로컬 backups/        빠른 복구
  백업2   암호화 → 클라우드          L-1 + 랜섬웨어 + 화재·도난
```

### 2. 암호화는 `age` 공개키 방식

```
pg_dump -Fc  →  age -r <공개키>  →  업로드
```

**공개키로 암호화하므로 서버에는 개인키가 없어도 된다.** 서버가 감염되어도 **과거 백업을 복호화할 수 없다.** 대칭키·비밀번호 방식이면 서버에 복호화 수단이 남아 이 이점이 사라진다.

| 키 보관처 | 판정 |
|---|---|
| 서버 PC | ❌ 감염 시 무의미 — 암호화한 의미가 사라짐 |
| **비밀번호 관리자** | ✅ 권장 |
| **종이에 적어 오프라인 보관** | ✅ 가장 확실 |

> **키를 잃으면 백업이 없는 것과 같다.** 복구 리허설에 **복호화 단계를 반드시 포함**한다.

### 3. 클라우드 동기화 폴더에 백업을 두지 않는다

**랜섬웨어는 연결된 드라이브를 따라간다.** 구글 드라이브 동기화 폴더에 백업을 넣으면 암호화된 파일이 그대로 동기화되어 **클라우드 사본까지 오염**된다.

→ **동기화 폴더가 아니라 API/rclone으로 업로드**한다. 클라우드의 버전 기록(구글 드라이브 30일)은 최후 수단이지 1차 방어가 아니다.

### 4. 로컬 노출을 최소화한다 (비용 ≈ 0)

| 조치 | 변경 |
|---|---|
| DB 비밀번호 강화 | `ledger` → 무작위 강한 값 (`.env`로 분리, git 제외) |
| **포트 바인딩 제한** | `"5432:5432"` → **`"127.0.0.1:5432:5432"`** — 같은 내부망의 다른 기기에서 직접 접근 차단 |
| 백업 디렉터리 | `.gitignore`에 `backups/` 추가, 권한 `0600` |

### 5. 로그인 화면은 여전히 2단계로 미룬다 — 다만 이유가 바뀐다

| 조치 | 비용 | 감염 시 효과 |
|---|---|---|
| DB 비밀번호·포트 제한 | ≈ 0 | ⭕ |
| **백업 암호화 + 오프사이트** | 낮음 | ✅ **랜섬웨어 방어의 핵심** |
| 로그인 화면 | 중간 | △ **감염된 PC에선 세션 쿠키도 함께 털린다** |

**앞의 두 개는 1단계에 넣는다.** 로그인 화면은 감염 대비 효과가 낮으므로 2단계 유지.

> 초판의 근거 *"내부망이라 안전하다"* 는 **철회**한다. 새 근거는 *"감염 대비에는 다른 조치가 더 효과적이다"* 이다.

## 결과

- ✅ 랜섬웨어 시나리오에 실질적 방어선 확보 (오프사이트 암호화 사본)
- ✅ 클라우드를 **신뢰하지 않아도** 됨 — 계정이 털려도 데이터는 안전
- ✅ 서버 감염 시에도 **과거 백업은 복호화 불가** (공개키 방식)
- ✅ 비용 거의 없는 조치(비밀번호·포트)로 가장 직접적인 침투 경로 차단
- ⚠️ **키 분실 = 백업 상실.** 복구 리허설에 복호화를 반드시 포함
- ⚠️ 업로드 자동화(rclone 등)에 클라우드 자격증명이 서버에 남는다 → **쓰기 전용 권한**으로 제한하고, 이 자격증명으로 **기존 백업을 삭제·덮어쓸 수 없게** 한다

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| **도커 볼륨 암호화** | 가동 중에는 복호화 상태로 마운트되어 감염·랜섬웨어에 무용. 비용만 발생 |
| **백업을 클라우드 동기화 폴더에 배치** | 랜섬웨어가 동기화를 타고 클라우드 사본까지 오염 |
| **대칭키(비밀번호) 암호화** | 서버에 복호화 수단이 남아 감염 시 과거 백업까지 노출 |
| **1단계부터 로그인 화면 도입** | 감염된 PC에서는 세션도 탈취되므로 효과가 제한적. 같은 노력으로 백업 암호화가 훨씬 효과적 |
| 클라우드 백업 포기(로컬만) | L-1(디스크 고장)·화재·도난에 무방비. 3-2-1의 `1`이 사라짐 |
