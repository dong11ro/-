## 1. 개요

### 1.1 목적

12년째 엑셀로 운영 중인 가계 재무 시스템을, **분류 노동을 자동화한 웹 애플리케이션으로 대체**한다.
단, 사용자가 **소비를 되돌아보는 행위(자각)는 보존**한다.

### 1.2 범위

| 포함 | 제외 |
|---|---|
| 거래 수집(파일) · 자동 분류 · 확인 · 저장 · 정합성 검증 | 은행 자동 연동 (규제상 불가) |
| 훑기·통계 화면 | 자산·투자 평가손익 (별도 모듈) |
| 12년치 엑셀 마이그레이션 | AI 질의 (MVP 이후) |

### 1.3 용어

→ [05_arc42 §12 용어집](05_arc42_아키텍처.md) 참조. **"품목"은 두 층위를 가리키므로 이 문서에서는 `분류`와 `상세명(item_name)`으로 분리해 쓴다.**

## 2. 전체 설명

### 2.1 사용자

| | P2. 아빠 (1차) | P1. 나 (2차·개발자) |
|---|---|---|
| 특성 | 비개발자, 12년 운영 파워유저, AI 도구 사용 경험 있음 | 개발자 |
| 목적 | **소비를 되돌아보고 쓸데없는 소비를 억제** | 아빠 카드 포함 내 지출 파악 |
| 전환 시점 | **P1이 검증한 뒤** (2.4 참조) | 개발 초기부터 |

### 2.2 제약

→ [05_arc42 §2](05_arc42_아키텍처.md). 요약: **규제상 자동 연동 불가 / 아빠 PC ≠ 서버 / 1인 개발 / 12년치 기존 시스템 가동 중**

### 2.3 가정

| ID | 가정 | 틀렸을 때 |
|---|---|---|
| A-1 | 아빠가 은행·카드 파일을 직접 내려받을 의사가 있다 | 수집 자체가 불가 → 제품 무의미 |
| A-2 | 오빠두 템플릿이 현재도 동작한다 | 네이버·쿠팡이 블랙박스로 남음 (은행 경로는 생존) |
| A-3 | 12년치 엑셀 구조가 전 구간 일관적이다 | 변환 가능한 구간까지만 이관 (R-7) |
| A-4 | LLM이 한국어 상품명을 분류할 수 있다 | 목표 85% 미달 → 임계 하향 |

### 2.4 도입 전략 — 2단계

**R-8(병행 운영 중 이중 입력)을 구조적으로 회피하는 핵심 결정이다.**

```
[1단계]  P1(나)만 사용                      아빠는 엑셀만 계속 사용
         · 내 데이터로 분류 엔진 검증           · 이중 입력 없음, 부담 0
         · 외부 LLM 실험 가능 (내 데이터)       · 미완성 리스크를 내가 감당
              ↓  통과 조건: 아래 2.5
[2단계]  아빠 전환 (cutover)
         · 12년치 마이그레이션 → 검증 → 엑셀 중단
```

**이 전략이 R-8을 "병행 운영 설계"에서 "전환 시점 설계"로 축소시킨다.**

### 2.5 2단계 진입 조건 (Gate)

| 조건 | 판정 |
|---|---|
| P1이 **4주 이상 실제로 사용** | ⚠️ v1 실패 원인이 "내가 안 썼다"이므로 **이것이 최우선 신호** |
| 자동 분류율 ≥ 70% (내 데이터) | 측정 |
| 정합성 검증에서 미해결 불일치 0건 | 측정 |
| 마이그레이션 dry-run 성공 | 아빠 데이터 사본으로 |

> **P1이 안 쓰면 2단계로 넘어가지 않는다.** 안 쓰는 것 자체가 "아직 쓸 만하지 않다"는 신호다.

## 3. 기능 요구사항 (FR)

각 요구사항에 **수용 기준(AC)** 을 붙인다. **AC는 테스트 가능한 문장이어야 한다** — G1 승인 기준.

### 3.1 수집

| ID | 요구사항 | 수용 기준 (AC) | 등급 |
|---|---|---|---|
| **FR-01** | 기관별 파일을 업로드해 거래 후보로 변환한다 | 우리은행·우체국·KB·오빠두(네이버/쿠팡) 파일 각각에 대해, 샘플 파일을 넣으면 날짜·금액·가맹점명이 올바르게 추출된다 | **M** |
| **FR-02** | 새 기관 추가는 파서 함수 하나로 끝난다 | 파서 함수 1개 + 레지스트리 등록만으로 신규 형식이 동작하고, 기존 파이프라인 코드는 변경되지 않는다 | **M** |
| **FR-03** | 원본 가맹점명을 원문 그대로 보존한다 | 저장된 거래의 `raw_merchant`가 파일 원문과 문자 단위로 일치한다 | **M** |

| **FR-05** | 중복 거래를 감지한다 | 승인번호가 있으면 그것으로, 없으면 (날짜+유형+금액+가맹점) 지문으로 판정한다. **같은 날 같은 가맹점 같은 금액의 서로 다른 승인번호 2건은 중복이 아니다** | **M** |

## 5. MoSCoW 우선순위 맵

### Must — 없으면 제품이 성립하지 않는다

`FR-01,02,03,05` 수집 · `FR-06~11` 분류 · `FR-12~16` 데이터모델 · `FR-17,18` 검증 · `FR-19,20` 훑기 · `FR-23` 집계API · `FR-26~28` 마이그레이션

### Should — 중요하나 없어도 출시 가능

`FR-04` 원본 파일 보관 · `FR-21` 컴포넌트 재사용 · `FR-22` 통계 화면 · 카드사 파서 확대

### Could — 있으면 좋다

`FR-24` AI 질의 · `FR-25` 자산·투자 · 예산 기능 · 태그

### **Won't (이번 사이클에서 하지 않는다)** ← 명시가 목적

| 항목 | 사유 |
|---|---|
| **거래 1:N 품목 테이블** | MVP에 사용처 없음. 양방향 문 → [ADR-002](adr/ADR-002-품목은-컬럼으로.md) |
| **품목 단위 입력 UI** | 노동을 늘림. 자동 유입 품목으로 목적 달성 |
| **영수증 OCR** | 품목의 실현 수단이나 난이도 높음. 다음 사이클 |
| **결제 알림 수집 (경로 C)** | 24시간 서버 필요. 오빠두로 커버리지 해결됨 |
| **은행 자동 연동** | **규제상 불가** → [ADR-004](adr/ADR-004-수집경로.md) |
| **Cowork·외부 노출** | 인터넷 노출·OAuth를 MVP에 끌어들임 → [ADR-007](adr/ADR-007-AI연동-유예.md) |
| **예산 기능** | v1엔 있으나 **아빠 엑셀엔 없음.** 아빠 요구가 확인되면 재검토 |

> **`Won't`를 적는 이유**: 목록에서 그냥 빼면 나중에 *"이건 왜 없지?"* 가 반복된다. 실제로 이번 설계에서 자금주체 축이 3번, 품목 테이블이 2번 뒤집혔다.

## 6. North Star Metric

### 확정: **자동 분류율**

```
              자동 확정된 거래 수
NSM  =  ────────────────────────  × 100
                전체 거래 수

베이스라인   32%   (아빠 실측 — Claude Log "57개 중 18개")
이관 직후    45%   (이력 씨딩만으로 — FR-27)
목표         85%   (FR-08)
```

**측정**: 2018~2024로 구성 → **2025~2026 홀드아웃**으로 평가. 랜덤 분할이 아닌 **시간 분할**(미래 정보 누수 방지).

### 원안(자동 입력율)을 기각한 이유

Step 1에서는 페인을 *"수기 입력"* 으로 봤으나, 실측 결과 **원본 적재는 이미 하고 계셨고 병목은 분류**였다. 지표가 페인을 안 재면 의미가 없다.

### 가드레일 (NSM 조작 방지)

| 지표 | 기준 | 왜 필요한가 |
|---|---|---|
| **오분류율** | ≤ 5% (FR-09) | 전부 자동확정하면 NSM 100% → **품질로 제동** |
| **고액 확인율** | 임계 이상 100% 확인 (FR-10) | 오분류 비용이 큰 롱테일 보호 |
| 월간 정리 실행 | ≥ 1회 | 분모 방어 |

> **NSM은 목표가 아니라 나침반이다.** "85% 달성"이 목적이 아니라 **기능을 넣을지 뺄지 판단하는 기준**으로 쓴다.

전체 이관이 오히려 유리하다: ① 22,047건은 DB에 사소한 규모 ② **상세명 매핑 8,521개가 곧 분류 규칙**이므로 자를수록 초기 자동분류율이 떨어짐 ③ 12년 시계열은 엑셀이 주는 가장 귀한 자산 ④ 나중에 자르는 건 기간 필터 한 줄, 채우는 건 어려움.

## 9. 변경관리 규칙 (G1 이후)

**동결은 변경 금지가 아니라 "슬쩍 바꾸지 못하게" 하는 것이다.**

| 변경 종류 | 절차 |
|---|---|
| AC 문구 조정 | SRS 개정 이력에 기록 |
| **요구사항 추가·삭제** | ① MoSCoW 재평가 ② RTM 갱신 ③ SRS 개정 이력 |
| **아키텍처 결정 변경** | **ADR 신규 작성** (기존 ADR은 `Superseded`로 표시, 삭제 금지) |
| NSM·가드레일 변경 | 근거 데이터 첨부 필수 |

> 이번 설계에서 판정이 뒤집힌 12건([01 §9-A](01_제품비전.md), [02-A §5](02-A_요구사항_추출.md))은 전부 **기록으로 남겼기 때문에** 같은 논의를 반복하지 않았다. 이 규칙의 목적이 그것이다.
