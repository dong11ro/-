## 2. 제약조건 (Constraints)

**아키텍처 선택지를 좁힌 조건들.** 기술 선택의 근거 절반이 여기 있다 — 많은 결정이 "이게 최선이라서"가 아니라 **"다른 선택지가 없어서"** 내려졌다.

### 2-1. 법·규제 제약 (가장 강함)

| 제약 | 근거 | 결과 |
|---|---|---|
| 은행 웹 자동 스크래핑 불가 | 전자금융거래법 위반 시 5년 이하 징역·3천만원 이하 벌금. 은행 약관이 스크래핑을 별도 계약 서비스로 규정. FDS가 자동 로그인 탐지·차단 | **자동 연동 아키텍처 전면 배제** |
| 오픈뱅킹 API 불가 | 개인은 테스트베드만. 실서비스는 금융결제원 승인 + 최소 개인사업자 + 보안점검 포함 천만원대 | 동일 |
| 마이데이터 불가 | 금융위 허가 필요 | 동일 |

> **핵심**: "은행에서 자동으로 가져온다"는 **기술적으로 어려운 게 아니라 법적으로 불가능**하다.
> 따라서 수집 계층은 **사용자가 내려받은 파일을 받는 구조**로 고정된다. → [ADR-004](adr/ADR-004-수집경로.md)
> 이 제약은 우회 대상이 아니라 **설계의 출발점**이다.

### 2-2. 환경 제약

| 역할 | 환경 | 함의 |
|---|---|---|
| 개발 | **MacBook** (Apple Silicon) | GPU 없음 → 로컬 LLM 개발이 운영과 불일치 |
| 운영 서버 | **Windows 데스크탑**, RTX 3060 12GB, Ryzen 7 7800X3D | 로컬 LLM 가능. **단 상시 가동 아님** |
| 클라이언트 | 아빠 PC(Windows), 본인 iPhone/Mac | 같은 집 내부망 |
| 네트워크 | 가정용 회선, 고정 IP 없음 | 외부 노출 시 별도 장치 필요 |

> ⚠️ **아빠가 쓰는 PC와 운영 서버 데스크탑은 다른 기기다.** (08-29 확인) — 같은 내부망이지만 같은 머신이 아니다.

**파생 제약**
- 서버가 24시간 떠 있지 않으므로 **푸시·알림 수신형 아키텍처는 불가** (경로 C 보류 사유)
- 개발(Mac)과 운영(Windows)의 OS 차이 → **컨테이너화가 선택이 아니라 필수**
- **오빠두 템플릿은 Windows 엑셀 전용** → 수집 작업 자체가 특정 기기에 묶임
- **아빠 PC ≠ 서버**이므로, 같은 머신을 전제하는 통합(예: stdio 기반 로컬 연동)은 한 단계를 더 거쳐야 한다

### 2-2-1. 발견 — 클라이언트 선택이 네트워크 노출을 결정한다 (08-29)

AI 질의 연동을 검토하며 드러난 제약이다. 보통은 *서버를 만들고 클라이언트를 붙인다*고 생각하지만, 여기서는 반대였다:

| 클라이언트 | 요구되는 네트워크 구조 |
|---|---|
| Claude **Cowork** | Remote MCP만 지원 → **서버를 공인 인터넷에 노출** + OAuth + 상시 가동 |
| Claude **Desktop** | Local MCP 가능 → 노출 불필요. 단 **같은 PC 안**에서만 성립 |
| **우리 앱 내장** | 노출 불필요, 추가 설치 없음 |

*"아빠가 Cowork를 쓸 것 같다"* 는 한마디가 **인터넷 노출·인증·상시가동을 전부 끌고 들어왔다.**
→ 이 경로는 MVP에서 배제했다 ([ADR-007](adr/ADR-007-AI연동-유예.md)).
→ **교훈: 통합 대상 클라이언트를 정하는 것은 UI 결정이 아니라 인프라 결정이다.**

### 2-3. 인적·조직 제약

| 제약 | 함의 |

| **개발자와 사용자가 같이 삶** | 온보딩·장애대응을 대면으로 해결 가능 → 원격 지원·자동복구 요구가 낮아짐 (드문 이점) |

### 2-5. 시스템 컨텍스트 (arc42 §3)

```
        [사람]                    [우리 시스템]                [외부]

   아빠 (주 사용자) ──업로드──▶ ┌──────────────┐
   본인 (부 사용자) ──조회───▶ │   가계부 v2   │
                              │              │
                              └──────┬───────┘
                                     │
                            (파일만 오간다. 실시간 연동 없음)
                                     │
   우리은행·우체국 ──xls──────────────┤
   카드사        ──엑셀─────────────┤
   오빠두 템플릿 ──xlsx────────────┘   ← 네이버페이·쿠팡을 우회 수집
                     ↑
              (사람이 직접 다운로드)

   LLM 백엔드 ◀──분류 질의──  (로컬 Ollama 또는 외부 API — 실측 후 확정)

**중요**: 시스템은 **어떤 외부 서비스와도 실시간으로 연결되지 않는다.** 유일한 외부 의존은 LLM 백엔드뿐이며, 그마저 로컬로 대체 가능하다. → 외부 장애가 우리 시스템을 멈추지 못한다.

## 4. 솔루션 전략 (Solution Strategy)

품질 목표 → 아키텍처 접근 → 기술 선택의 매핑. **이 표가 기술 스택의 근거다.**

| # | 품질 목표 | 아키텍처 접근 | 기술 선택 | 근거 |
|---|---|---|---|---|
| **Q1** | **자동 분류율 85%** (NSM) | 4계층 분류 엔진, 상위 계층 우선. 교체 가능한 백엔드 | Python (LLM·ML 생태계), `Classifier` 인터페이스 | 이력만으론 45%가 상한 — 실측 근거 [04 4절](04_1차설계.md) |
| **Q2** | **자각 보존** (P-1) | 자동 확정 건도 훑기 목록에 노출. 확인 화면 = 회고 화면 | React 컴포넌트 재사용 | [ADR-006](adr/ADR-006-자각-보존.md) |
| **Q3** | **데이터 신뢰성** — 남의 12년치를 다룸 | 원본 보존 + 잔액 정합성 검증 + 스키마 버전관리 | PostgreSQL(트랜잭션·제약), **Alembic** | 유실은 곧 신뢰 상실 → 즉시 이탈 (R-3) |
| **Q4** | **수집 확장성** — 기관이 계속 늘어남 | 파서만 교체, 이후 파이프라인은 공통 | `PARSERS` 레지스트리 (v1 자산) | 기관 추가 = 함수 1개 |
| **Q5** | **낮은 운영 부담** — 1인 개발, 비개발자 사용 | 단일 호스트, 컨테이너 3개, 외부 의존 없음 | Docker Compose (K8s 아님) | 제약 2-3 |
| **Q6** | **개발↔운영 재현성** | 전 구성 컨테이너화 | Docker | Mac↔Windows OS 차이 흡수 |
| **Q7** | **프라이버시** | 외부 전송 최소화, 실험은 본인 데이터로 | 로컬 LLM 우선 검토 | 아빠 금융정보 |
| **Q8** | **개선의 증명 가능성** | 정답셋 기반 회귀 테스트 | **pytest** (v1엔 0개) | 22,047건 라벨 보유 → 정확도를 숫자로 |

### 전략의 요약

> **"바깥과 끊고, 안에서 정확하게."**
> 규제가 외부 연동을 막았으므로 아키텍처의 승부처는 **연동이 아니라 분류 정확도**다.
> 따라서 복잡도 예산의 대부분을 **분류 엔진과 검증**에 쓰고, 나머지(인프라·배포·UI 프레임워크)는 **가장 단순한 선택**을 유지한다.

### 기술 선택이 "선택이 아니었던" 것들

정직하게 구분한다. 아래는 **비교 검토의 결과가 아니라 제약의 귀결**이다:

| 기술 | 실제 이유 |
|---|---|
| React·FastAPI·PostgreSQL·Docker | **v1 확장 결정으로 자동 승계.** 재비교하지 않았다 ([ADR-001](adr/ADR-001-v1-확장.md)) |
| 파일 업로드 수집 | **법적으로 다른 선택지가 없음** |
| Docker | Mac↔Windows 차이 흡수 외 대안 없음 |
| Python | v1 승계 + LLM 생태계 |

**새로 비교 검토한 것은 LLM 백엔드 하나뿐**이며, 그마저 "지금 결정하지 않는다"가 결론이다 ([ADR-005](adr/ADR-005-LLM-교체가능-인터페이스.md)).

## 5. 빌딩블록 뷰 (Building Block View) — C4

> **arc42 §5와 C4의 레벨 대응** (용어가 겹쳐 혼동되므로 명시)
>
> | C4 | arc42 §5 | 무엇을 그리나 |
> |---|---|---|
> | Level 1 Context | (§3 컨텍스트) | 시스템 1개 + 사람 + 외부 시스템 |
> | **Level 2 Container** | **Level 1** | **실행·배포되는 단위** |
> | Level 3 Component | Level 2 | 컨테이너 하나의 내부 |
>
> **Container는 Docker 컨테이너가 아니다.** 판별기준: ①별도 프로세스로 실행 ②따로 배포·재시작 ③프로세스 경계를 넘는 통신 — 셋 다 예여야 Container.

### C4 Level 1 — Context

```

   │  주 사용자    │                      │  부 사용자·개발│
   └──────┬───────┘                      └──────┬───────┘
          │ 업로드 / 분류확인 / 훑기               │ 조회·탐색
          ▼                                     ▼
   ╔═══════════════════════════════════════════════════════╗
   ║                    가계부 v2                           ║
   ║   거래를 수집·분류·저장하고, 소비를 되돌아보게 한다       ║
   ╚═══════════════════════════┬═══════════════════════════╝
                               │ 분류 질의
                    ┌ ─ ─ ─ ─ ─▼─ ─ ─ ─ ─ ┐

**이 그림의 핵심**: 우리 시스템은 **외부와 직접 연결된 곳이 거의 없다.** §2의 규제 제약이 그림 한 장으로 드러난다.

|---|---|

| 마이그레이션 | ❌ API가 제공하는 일회성 작업. 별도 프로세스가 아니면 컨테이너가 아님 |
| **HDD** | ❌ **실행되지 않음.** 물리 장치는 §7 배포 뷰의 요소 |
| 오빠두 템플릿 | ❌ 아빠가 쓰는 **외부 도구**. Level 1에 표기 |

### C4 Level 3 — API 내부

```
API
├── 수집 파이프라인
│   ├── Parser (레지스트리)        우리은행 · 우체국 · 카드 · 오빠두 · 수동
│   ├── Normalizer                 거래 후보 형태로 통일
│   └── Deduplicator               승인번호 → 조합지문 폴백
│
├── 분류 엔진  (Classifier 체인)
│   ├── HistoryClassifier          상품명 완전일치   커버 45% · 정확 97%
│   ├── BizNoClassifier            사업자번호 정확매칭
│   ├── KeywordClassifier          규칙 부분일치
│   └── LLMClassifier              ← 백엔드 교체 가능
│
├── 확인 정책  (ConfirmPolicy)     신뢰도·금액 임계 → 자동확정 / 확인요청
│
├── 정합성 검증 (Reconciler)       거래후잔액 대조 → 누락·중복 경고
│
├── 집계 (Aggregator)              ★ 범용: 기간·분류·주체·축을 파라미터로
│                                     화면·AI·MCP가 모두 이것을 쓴다
│
└── 마이그레이션                     엑셀 → DB (분류 매핑 씨딩 포함)
```

### 각 블록의 책임

| 블록 | 무엇을 하나 | 무엇에 의존하나 |
|---|---|---|
| Parser | 파일 → 거래 후보 (기관 형식 흡수) | 없음 (순수 함수) |
| Deduplicator | 이미 있는 거래인지 판정 | DB 조회 |
| Classifier | 거래 후보 → (분류, 신뢰도, 근거) | 규칙 테이블, LLM |
| ConfirmPolicy | 사람 확인이 필요한지 판정 | 신뢰도·금액 |
| Reconciler | 계좌 잔액과 대조해 누락 탐지 | DB |
| 마이그레이션 | 12년치 이관 + 규칙 씨딩 | Parser 재사용 |

**설계 의도**: Parser와 Classifier는 **순수 함수에 가깝게** 유지한다. 둘 다 정답셋으로 단위 테스트가 가능해야 하고, 이것이 Q8(개선의 증명 가능성)의 전제다.

## 8. 횡단 개념 (Cross-cutting Concepts)

여러 블록을 관통하는 공통 메커니즘. **한 곳에서 정의하고 모두가 따른다.**

### 8-1. 수집 파이프라인 — "다른 것은 획득 방법뿐"

```
소스별로 다른 것:  fetch/parse (파일 형식)
모두 공통인 것:    정규화 → 중복감지 → 분류 → 확인 → 저장 → 검증
```

새 기관 추가 = **파서 함수 1개 등록.** 나머지 코드는 불변.
(v1 `importer.py`의 `PARSERS` 딕셔너리가 이미 이 구조)

### 8-2. 분류 — 계층 + 신뢰도 + 근거

모든 분류 결과는 **세 가지를 함께** 반환한다:

```
(category_id, confidence, reason)
                            ↑ "사업자번호 일치" / "과거 3회 동일" / "LLM 추론"
```

`reason`은 선택이 아니라 **필수**다. 사용자가 제안을 신뢰할지 판단하는 근거이고(P-1), 분류기를 디버깅하는 유일한 단서다.

### 8-3. 중복 감지 — 2단계 키

| 순위 | 키 | 적용 |
|---|---|---|
| 1 | **승인번호** (`external_ref`) | 카드 명세 |
| 2 | 조합 지문 (날짜+유형+금액+가맹점) | 승인번호가 없는 소스 |

> v1 결함: 승인번호를 안 쓰고 조합 지문만 사용 → **같은 날 같은 편의점 같은 금액 재결제를 중복으로 오판**. 아빠 데이터에서 편의점·군것질이 건수 상위라 실제로 발생할 시나리오다.

### 8-4. 정합성 검증 — 잔액 대조

은행이 준 `거래후잔액`을 보존하고, 우리 계산과 대조해 **누락·중복을 탐지**한다.
엑셀이 이미 하고 있는 검증이며, **없으면 신뢰를 잃는다.**

### 8-5. 분류 코드 — 내부 표현과 외부 표현의 분리

| 층 | 표현 | 이유 |
|---|---|---|
| 내부 | `parent_id` 정규화 계층 | 조회·집계에 적합 |
| 외부 | 11자리 코드 `10101001001` | **12년치 데이터의 조인 키**, 아빠와의 공통 어휘 |

엑셀이 코드에 계층을 인코딩한 것은 FK가 없어서였다(도구 제약). 그러나 코드 자체는 **버리면 안 되는 자산**이다.

### 8-6. 자금 주체 (`bearer`)

`self` / `child` / `shared`. 카테고리·소비구분과 **독립된 횡단 축**이다.
집계 시 *"내 지출"* 과 *"아들 지출"* 을 분리할 수 있어야 한다 — 아빠 엑셀의 `지출-(동현+제외)` 수식이 이 요구의 증거.

### 8-7. 오류 처리 원칙

| 상황 | 원칙 |
|---|---|
| 분류 실패 | **에러가 아니다.** `미분류`로 저장하고 확인 대기열로 |
| 파싱 실패 | 해당 행만 건너뛰고 **나머지는 저장**. 실패 행을 사용자에게 보고 |
| 중복 의심 | 자동 삭제 금지. **사용자에게 판단을 넘김** |
| 마이그레이션 | **멱등**하게 — 재실행해도 중복 생성되지 않아야 |

> 관통 원칙: **비개발자가 쓰므로, 실패해도 데이터가 손상되지 않아야 한다.** 부분 실패는 허용하되 조용한 손실은 허용하지 않는다.

## 12. 용어집 (Glossary)

**실제로 혼동이 발생했던 용어들이다.** 아빠 시스템과 우리 시스템의 어휘가 다르다.

| 용어 | 아빠 엑셀에서 | 우리 시스템에서 | 비고 |
|---|---|---|---|
| **품목** | ⚠️ **두 가지 의미** — `code` 시트에선 **최하위 분류명**(육류·어류), `지출` 시트에선 **실제 상품명**(너구리) | 쓰지 않는다. `분류`와 `item_name`으로 분리 | **최대 혼동원** |
| **분류 / 카테고리** | 5단계 계층 (구분>대분류>중분류>소분류>품목) | `categories` (parent_id 계층) | 302개 중 실사용 132개 |
| `가계부cd` | 11자리 코드 `10101001001` | `categories.code` | 이관 조인 키 |
| **거래** | `계좌 원장`에만 존재 (지출 원장엔 없음) | `transactions` 1행 | 아빠는 두 원장이 분리 |
| `기재내용` | 은행 원본 가맹점명 | `raw_merchant` | 추적성의 근거 |
| **제외** | 적금·투자를 지출 집계에서 빼는 플래그 | `categories.kind` (비소비) | |
| **소비성/비소비성** | 대분류 이름 자체 | `kind` 컬럼 | ADR-003 |
| **(동현)** | 분류명 접미사로 주체 표시 | `bearer` 컬럼 | 라벨이 아니라 축으로 승격 |
| **자동 분류율** | — | NSM. `자동 확정된 건 ÷ 전체` | 현재 베이스라인 32% |
| **훑기 (scan)** | — | 내역을 쭉 보며 자각하는 행위·화면 | 제품의 중심 개념 |
| **오빠두 템플릿** | 쿠팡 시트의 출처(추정) | 네이버·쿠팡 수집 경로 | 외부 자산 |
