## 4. 발견된 결함

### 결함 ① `kinds.py` — 이름 기반 하드코딩

```python
KIND_BY_TOP = {"저축": "saving", "투자": "investment", "이체": "transfer"}

def kind_of(top_name): return KIND_BY_TOP.get(top_name or "", "consumption")
```

**대분류의 "이름 문자열"로 소비/비소비를 판정한다.** 세 가지 문제가 있다:

1. **아빠 분류 체계로 교체하는 순간 전부 깨진다.** 아빠의 대분류는 `소비성지출 / 비소비성지출`이라 이 딕셔너리에 하나도 안 걸린다 → 전부 `consumption`으로 오판.
2. 사용자가 카테고리 이름을 바꾸면 조용히 오작동한다. **실패가 드러나지 않는 종류의 버그**다.
3. 프로젝트 자체 설계 원칙 위반 — 명세서 1장: *"설계 원칙: 하드코딩 배제"*

→ **`Category.kind` 컬럼으로 데이터화.** 판정이 데이터에 있으면 분류 체계를 갈아끼워도 안전하다.

### 결함 ② 중복 감지 지문이 약하다

```python
def fingerprint(date, type_, amount, merchant):
    return f"{date}|{type_}|{amount:.2f}|{merchant or ''}"
```

`external_ref`(중복감지용) 컬럼을 만들어놓고 **실제로는 조합 지문을 쓴다.** 같은 날 같은 편의점에서 같은 금액을 두 번 결제하면 **정상 거래가 중복으로 오판**된다. 아빠 데이터에 편의점·군것질이 대량(건수 상위 3위)이라 실제로 발생할 시나리오다.

→ 카드 명세의 **승인번호**를 `external_ref`에 넣고 1순위 키로. 승인번호가 없는 소스만 조합 지문으로 폴백.

### 결함 ③ 인증 없이 `user_id`만 존재

모든 테이블에 `user_id = Column(Integer, default=1)`이 있지만 **인증이 없다.** 2인 제품이 되면 이 컬럼들은 보호받지 못한다. → Step 4(보안·NFR)에서 다룬다.

### 결함 ④ 테스트 0개

`backend`에 테스트 파일이 없다. 회고의 "3중 검증"은 **수동**이었다. 분류 엔진은 정확도가 곧 제품 가치라 **테스트 없이는 개선 여부를 알 수 없다.** → Step 7(TDD)의 최우선 대상.

## 5. 최종 판정 — 확장한다

| 선택지 | 판정 |
|---|---|
| **① 확장 (v1 진화)** | ✅ **채택** |
| ② 전면 재작성 | ❌ 불필요 |

### 근거

1. **인프라·파이프라인·프론트 패턴이 그대로 유효하다.** 재작성하면 회고에 기록된 삽질 5건을 다시 겪는다.
2. **변경 범위가 테이블 3개 수정 + 3개 신설로 한정된다.** `importer`·`budget`·`ImportPreset`·`SavedFilter`는 손댈 필요가 없다.
3. **Alembic이 이미 있다.** 스키마 진화 경로가 확보되어 있다 — 회고에서 "잘한 결정"으로 꼽은 것이 여기서 값을 한다.

### 그리고 결정적으로 — **v1을 안 썼기 때문에 자유롭다**

v1의 실패(한 번도 제대로 안 씀)가 여기서 **자산으로 바뀐다.** 실데이터가 거의 없으니 `Transaction`을 헤더/라인 구조로 쪼개는 큰 수술을 **데이터 손실 걱정 없이** 할 수 있다.

> 회고의 용어로: 실사용 데이터가 없으므로 스키마 변경이 **단방향 문에서 양방향 문으로 바뀌었다.**
