## 0. 이 문서가 존재하는 이유

02 초판은 관찰을 곧바로 요구사항으로 옮겼다. *"302개 코드를 그대로 가져온다", "품목 단위를 지원해야 한다"* — **베끼기 계획이었다.**

그대로 가면 결과는 **DB로 엑셀을 흉내 낸 물건**이다. 최악의 설계다. 기존 시스템의 구조에는 두 가지가 섞여 있기 때문이다:

```
관찰된 구조 = 진짜 요구사항  +  도구의 한계에 대응한 흔적
                              ↑ 이걸 옮기면 한계까지 물려받는다
```

**기존 시스템을 대체하는 프로젝트의 첫 번째 과제는, 그 시스템에서 "요구사항"과 "우회책"을 분리하는 것이다.**

## 1. 판정 기준

세 가지 테스트를 통과하는지로 판정한다.

| 테스트 | 질문 | 실패 시 |
|---|---|---|
| **T1. 이식** | 도구를 바꿔도(DB·종이·타 서비스) 이 구조가 필요한가? | 도구 제약 → **버림** |
| **T2. 제거** | 없애면 아빠가 답을 못 얻는 질문이 생기는가? | 불필요 → **버림** |
| **T3. 목적** | 이것이 어떤 **의사결정**을 돕는가? | 목적 불명 → **보류** (물어봐야 함) |

T3을 통과 못 한 항목을 **함부로 채택하지 않는 것**이 이 문서의 핵심 규율이다. "쓰고 계시니까 필요하다"는 근거가 아니다 — **관성일 수 있다.**

## 3. 데이터로 판정 — 분류 체계를 단순화할 것인가

### 검증한 가설

> **H-단순화**: "302개 분류가 많아서 자동 매칭률이 32%로 낮다. 분류를 줄이면 페인이 줄어든다."

### 결과: **기각**

22,047건 전수 집계 (상세는 [02 문서 3절](02_아빠엑셀_분석.md)):

| 상위 N개 | 건수 커버리지 | 금액 커버리지 |
|---:|---:|---:|
| 30 | **89.5%** | **18.9%** |
| 100 | 99.7% | **89.8%** |

**분류를 상위 30개로 줄이면 건수의 90%는 처리되지만 금액의 81%를 잃는다.** 근로소득·이자소득·부모님용돈·병원비처럼 **드물지만 금액이 큰** 항목이 롱테일에 몰려 있기 때문이다.

→ 분류 체계 단순화는 **답이 아니다.** 132개 실사용 분류를 유지한다.
→ 단, 미사용 170개는 마이그레이션 대상에서 제외한다. (마스터에는 보존하되 기본 비활성)

### 그런데 이 기각이 더 좋은 설계 지침을 낳았다

건수 파레토와 금액 파레토가 **정반대**라는 사실이 자동화 전략을 그대로 규정한다:

```
상위 30개 분류   건수 90% / 금액 19%   →  ★ 자동화 대상
                                          반복 노동이 전부 여기 있음
하위 100개 분류  건수 10% / 금액 81%   →  ★ 사람 판단 유지
                                          드물어서 부담 없고, 틀리면 손해가 큼
```

**자동화가 필요한 곳과 정확도가 필요한 곳이 깔끔하게 분리된다.**

여기서 두 가지 설계 원칙이 도출된다:

1. **상위 30개 분류를 확실히 맞히는 것만으로 목표(85%)에 도달한다.** 분류기를 만능으로 만들 필요가 없다.
2. **금액이 큰 거래는 자동 확정하지 않고 사람 확인을 거친다.** 오분류 비용이 큰 쪽이 정확히 롱테일이므로, 신뢰도와 금액을 함께 보는 임계 정책이 필요하다.
