## 3. 분류 체계 — 5단계 계층 + 302 품목

`code` 시트 (166행):

```
구분        대분류           중분류      소분류       품목
────────────────────────────────────────────────────────
지출   >   소비성지출    >   생활비   >  식료품   >  육류·어류
소득   >   비소비성지출  >   교육     >  가전     >  조미·야채
                                                    (… 302개)
```

`지출cd` 시트 (302행) — 코드 부여:

| 컬럼 | 내용 |
|---|---|
| Rank No / cd | 정렬·식별 |
| **가계부cd** | 11자리 계층 코드 (예: `10101001001`) |
| 품목 / 구분 / 대분류 / 중분류 / 소분류 | 5단계 라벨 |
| **제외** | 적금·투자 등을 지출 집계에서 빼는 플래그 |

### v1.0.0과의 격차

| | v1.0.0 | 아빠 엑셀 |
|---|---|---|
| 계층 깊이 | 2단계 (대분류 > 소분류) | **5단계** |
| 분류 항목 수 | 약 30개 소분류 | **302개 품목** |
| 코드 체계 | 없음 (id 자동증가) | **11자리 의미 코드** |
| 소비/비소비 | `is_fixed` 등 별도 플래그 | **대분류 자체가 `소비성/비소비성`** |

**v1의 분류 체계는 아빠 기준으로 다운그레이드다.** 이걸 강요하면 12년치 데이터가 뭉개진다.

## 4. 원장·소스 스키마

### ④ `지출` — 통합 원장 (169,987행)

```
code | 분류 | 날짜 | 년 | 년월 | 품목 | 금액 | 지출 | 받은금액
```

품목 단위로 한 행. 즉 **영수증 한 장이 여러 행**이 된다. 17만 행의 정체.

### ② 계좌 원장 (예: `1{인물}우리`)

```
첫일 | 잔액 | 거래일자 | 적요 | 기재내용 | 찾은금액 | 맡긴금액 | 거래후잔액 | code | 품목 | 시작 | 동현card-match
```

| 관찰 | 시사점 |
|---|---|
| `기재내용` = 은행 원본 가맹점명 | v1의 `raw_merchant`와 동일 개념 — **추적성 확보를 이미 실천** |
| `거래후잔액` 보존 | **잔액 정합성 검증 가능** — v1엔 없는 개념 |
| `code` / `품목` | 원본 옆에 분류 결과를 나란히 둠 |
| **`동현card-match`** | 아들 카드 거래를 계좌 원장에서 식별하는 전용 컬럼 |

### ② `카드_{인물}` — 카드 명세 (149행)

```
날짜 | y-m-d h:m:0 | 승인번호 | 이용카드 | 이용가맹점(은행)명 | 사업자번호 | 이용구분 | 금액 | 취소금액 | 결제예정일 | code | 분류명
```

| 관찰 | 시사점 |
|---|---|
| **`사업자번호` 보유** | 가맹점 고유 식별자 → 문자열 매칭보다 정확한 분류 키 |
| `승인번호` | **중복 감지의 완벽한 자연키** |
| `취소금액` / `결제예정일` | 취소·할부 처리 개념 존재 |
| 분류명이 `외식(동현)`, `편의점(동현)` 형태 | **분류 라벨에 주체가 인코딩됨** |

### ② `쿠팡` (128행) / `영수증` (156행)

```
쿠팡:   거래일자 | 주문날짜 | 품목 | 단가 | 합계 | code | 품목명 | 조합 | 거래월
영수증: 날짜 | 상품명 | 단가 | 수량 | 금액 | 결제수단 | 가맹점 | code | 품목명
```

- **영수증을 상품 단위로 입력** — 단가·수량까지. 최고 강도의 수기 노동.
- 쿠팡 시트 데이터는 2026년 2월까지 존재 → **오빠두 템플릿을 이미 활용 중**으로 추정.

### ⑤ 집계 시트

| 시트 | 핵심 컬럼 |
|---|---|
| `지출소득내역` | 년월 / **동현** / 제외(적금·투자) / **지출-(동현+제외)** / 지출 / 소득 / 기타수입 / 현금(투자포함) / 쿠팡(품목개수) / 영수증(품목개수) / 쿠팡금액 / 영수증금액 |
| `월별내역` | 2018-1분기부터 분기 단위 141개 열 |
| `금융별잔액` | 은행code / 은행명(우리·신한·우체국 상품별·미래에셋·금·코인손익) / **합계(투자제외)·손익 / 합계(투자포함)·손익** |

> **`지출-(동현+제외)`** 이 수식 하나가 많은 걸 말해준다. 아빠는 "가계 지출"을 계산할 때 **아들 지출과 비소비성 지출을 빼고** 본다.

## 5. `Claude Log` 시트 — AI를 이미 쓰고 계신다

작업 로그 시트가 별도로 존재한다. 컬럼: `Turn # | Date | User Request | Action Taken | Details | Outcome`

기록된 작업(2026년 3월경, 최근):

- *"`1{인물}우리` 시트 E열 기재내용을 지출code와 매핑"* → **결과: 57개 중 18개 매칭**
- *"`5{인물}우체` 시트에서도 동일하게 E열 기재내용을 매핑"*
- *"`{인물}card-match`에 code 부여"* → **56행 전체 매칭 완료**
- *"code / 지출code / 지출_rankcd 3개 시트 수식 패턴 분석"*

### 이것이 의미하는 바

| 사실 | 시사점 |
|---|---|
| AI로 **가맹점명 → 분류코드 매핑**을 수행 중 | 우리가 만들려던 기능을 **수동으로** 이미 하고 계심 |
| 매칭률 57개 중 18개 (약 32%) | **자동 분류율이 낮다** — 개선 여지가 크고, 지표로 삼기 좋다 |
| 매번 대화로 수십 행씩 | **반복 노동이며 자동화 대상** |
| 작업 로그를 시트로 남김 | 추적·재현을 중시하는 성향 |

**아빠는 AI 도구에 대한 거부감이 없고, 이미 워크플로우에 편입시켰다.** R-1(전환 거부) 리스크를 크게 낮추는 근거다.

## 6. 실제 워크플로우 재구성

```
① 은행·카드·쿠팡·영수증에서 내역 확보
      ↓  (붙여넣기 / 오빠두 템플릿 / 손입력)
② 계좌·카드·쿠팡·영수증 시트에 원본 적재
      ↓  ★ 병목: 가맹점명 → 302개 code 매핑 (AI에게 매번 질의, 매칭률 ~32%)
③ 통합 원장(`지출`)으로 집약
      ↓  (엑셀 수식)
④ 월별·분기별 집계, 계좌 잔액·손익 산출
      ↓
⑤ 확인 — 다만 17만 행이라 파일이 무겁고 시각화에 한계
```

## 7. 진짜 페인포인트 — Step 1의 진단을 수정한다

| Step 1에서의 진단 | 실측 후 수정 |
|---|---|
| *"은행과 연결 안 됨 → **전부 수기 입력**"* | ❌ **부정확.** 원본 적재는 이미 하고 계심 |
| — | ✅ **진짜 병목은 ② 가맹점 → code 매핑.** 302개 분류에 손으로 배정, AI 질의로도 매칭률 32% |
| — | ✅ **영수증 품목 단위 입력** — 단가·수량까지 손으로 |
| *"데이터 쌓이면 느려짐"* | ✅ **확인됨.** 17만 행 + 계산체인 10MB |
| *"시각화 한계"* | ✅ 확인됨 (다만 집계 로직 자체는 정교함) |

### NSM 재검토 필요

Step 1에서 **자동 입력율**을 NSM으로 정했으나, 병목이 입력이 아니라 분류였다.
→ **`자동 분류율`(자동으로 올바른 code가 배정된 거래 비율)** 이 더 적합할 수 있다.
→ 현재 베이스라인이 **약 32%**로 측정되어 있다는 점이 강력하다. 개선을 숫자로 증명할 수 있다.

## 9. 설계 시사점

1. **자금 주체 축은 MVP 필수다.** Step 1에서 "양방향 문이므로 제외" 판정했으나 **철회.** 아빠 시스템의 핵심 축이며 집계 수식에까지 반영되어 있다.
2. **분류 체계는 아빠 것을 그대로 수용해야 한다.** 302개 품목·11자리 코드를 마스터 데이터로 가져온다. 우리 카테고리를 강요하면 12년치가 무의미해진다.
3. **품목 단위 기록을 지원해야 한다.** 거래(transaction) 1건에 품목(line item) N개 구조가 필요하다. v1의 평면 구조로는 영수증·쿠팡을 담을 수 없다.
4. **잔액 정합성 검증이 필요하다.** `거래후잔액`으로 누락·중복을 잡아내는 장치는 신뢰성의 핵심이다.
5. **사업자번호·승인번호를 1급 필드로.** 각각 분류 키와 중복 감지 자연키로 쓴다.
6. **자산·투자 모듈이 로드맵에 있어야 한다.** "엑셀 대체"를 목표로 하는 한 피할 수 없다.
7. **마이그레이션이 프로젝트의 일부다.** 12년치 17만 행을 옮기지 못하면 전환은 없다.
