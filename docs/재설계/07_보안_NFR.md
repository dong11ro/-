## 1. 위협모델 — STRIDE에 `L`을 더한다

### 1.1 왜 STRIDE만으로는 부족한가

STRIDE는 **악의적 공격자**를 전제한 틀이다. 그런데 우리 시스템은:

```
외부 공격자  →  직접 접근 경로 없음 (내부망 전용, 외부 노출 0)
내부자       →  사용자 2명, 가족, 같이 삶
```

> ### ⚠️ 초판 정정 (2026-08-31)
> 위 전제를 *"따라서 공격자가 없다"* 로 확대 해석했다. **틀렸다.**
> **PC가 감염되면 공격자가 내부망 안에 생긴다.** 감염 경로(메일 첨부·다운로드·USB·취약 소프트웨어)는 **방화벽과 무관**하다.
> → **M-1(맬웨어) · M-2(랜섬웨어)를 위협 목록에 추가**하고 [ADR-012](adr/ADR-012-감염-전제-방어.md)로 방어책을 정한다.

**직접적인 원격 공격자 모델은 비어 있다.** 그러나 감염을 전제하면 이야기가 달라진다. 교과서대로 적용하면 *"인증 강화, 감사 로그"* 라는 결론이 나오는데, 그건 우리 최대 위험이 아니다.

| 실제 시나리오 | STRIDE로 잡히나 |
|---|---|
| 디스크 고장 → 12년치 전손 | ❌ |
| 마이그레이션 재실행으로 중복·훼손 | ❌ |
| 잘못된 파일 업로드로 오염 | ❌ |
| 조작 실수로 분류를 뭉갬 | ❌ |
| LLM으로 데이터가 나감 | ✅ (I) |

→ **`L (Loss)` 축을 추가**한다. 유실·훼손이다.

### 1.3 신뢰 경계

| # | 경계 | 위험 | 이유 |
|---|---|---|---|
| **A** | 내부망 ↔ 외부 | 🟢 낮음 | 노출 없음. 단 공유기·타 기기 감염 시 무방비(인증 부재) |

## 2. 완화책

### L-1 · L-2 — 복구 이중화 → [ADR-011](adr/ADR-011-복구-이중화.md)

```
① DB 덤프 (pg_dump -Fc)     전체 상태 · 사람이 수정한 분류 포함
② 원본 파일 보관             재파싱으로 재구성 → RPO ≈ 0
```

**백업 시점은 시간이 아니라 사건에 건다** (서버가 상시 가동이 아니므로 cron 불가):

| 시점 | 이유 |
|---|---|
| 업로드 확정 직후 | 데이터가 변하는 순간 |
| **마이그레이션 실행 전** | L-2 방어. **백업 없이는 실행 자체를 막는다** |
| 앱 기동 시(마지막 백업 7일 초과) | 안전망 |

보관은 **최소 두 곳** — 서버 로컬 + 다른 물리 매체. 같은 디스크에 두면 L-1을 못 막는다.

> **FR-04(원본 파일 보관)를 `Should` → `Must`로 승격한다.** v1은 `file.read()` 후 원본을 버린다 — 복구 경로가 하나뿐이라는 뜻이다.

### M-1 · M-2 — 감염을 전제한 방어 → [ADR-012](adr/ADR-012-감염-전제-방어.md)

#### 암호화는 위협별로 효과가 다르다

*"도커 볼륨을 암호화하면 되지 않나"* 를 검토했고 **감염에는 효과가 없다**:

| 위협 | 디스크/볼륨 암호화 | **백업 암호화** |
|---|---|---|
| 디스크 도난·PC 폐기 | ✅ | ✅ |
| **악성코드 감염 (가동 중)** | ❌ **무용** | ⭕ |
| **랜섬웨어** | ❌ **무용** | ⭕ |
| 클라우드 업로드 유출 | — | ✅ |

가동 중에는 볼륨이 **복호화된 상태로 마운트**되어 있어 악성코드가 그냥 읽는다. 저장 시 암호화는 *"꺼진 디스크"* 를 지키는 기술이다.
→ **볼륨 암호화 대신 백업 암호화.** 디스크 암호화는 OS 기본 기능(BitLocker/FileVault)으로 충분(PC 폐기 대비).

#### 3-2-1 백업 + 오프사이트 암호화

```
3벌 원본+백업2  /  2개 서로 다른 매체  /  1개 오프사이트

  원본   서버 PC 볼륨
  백업1  서버 로컬 backups/           빠른 복구
  백업2  age 암호화 → 클라우드         L-1 + M-2 + 화재·도난
```

| 항목 | 결정 |
|---|---|
| 암호화 | **`age` 공개키 방식** — 서버에 개인키가 없어 **감염돼도 과거 백업을 복호화 못 함** |
| 키 보관 | 비밀번호 관리자 또는 **종이(오프라인)**. 서버에 두면 의미 없음 |
| 업로드 | ⚠️ **동기화 폴더 금지** — 랜섬웨어가 동기화를 타고 클라우드 사본까지 오염. rclone/API로 업로드 |
| 클라우드 자격증명 | **쓰기 전용**. 기존 백업을 삭제·덮어쓸 수 없게 |
| 복구 리허설 | **복호화 단계 포함 필수** — 키를 잃으면 백업이 없는 것과 같다 |

#### 로컬 노출 최소화 (비용 ≈ 0, 즉시)

| 조치 | 변경 |
|---|---|
| DB 비밀번호 | `ledger` → 무작위 강한 값 (`.env` 분리, git 제외) |
| **포트 바인딩** | `"5432:5432"` → **`"127.0.0.1:5432:5432"`** |
| 백업 디렉터리 | `.gitignore`에 `backups/`, 권한 `0600` |

### I-1 — LLM 전송 데이터 정책

**정책을 문서가 아니라 타입으로 강제한다.** LLM에 넘기는 DTO를 별도로 정의하고, 화이트리스트 밖의 필드는 구조적으로 실을 수 없게 한다.

| 전송 | 필드 | 이유 |
|---|---|---|
| ✅ 허용 | `item_name`, `raw_merchant` | 분류의 근거. 이것 없이는 분류 불가 |
| ✅ 허용 | `amount` (구간화 권장) | 금액대가 분류에 기여(고액=가전 등) |
| ❌ **금지** | 계좌번호, `balance_after`, 카드번호, `external_ref` | 분류에 불필요 · 민감도 최상 |
| ❌ **금지** | `biz_no` | 사업자번호는 **로컬 규칙 매칭용**이지 LLM 입력이 아니다 |
| ❌ **금지** | 개인 식별정보(이름·주소) | 애초에 저장하지 않음 |

**로컬 LLM(Ollama) 채택 시 경계 B가 소멸**하므로 이 정책의 부담이 사라진다 — [ADR-005](adr/ADR-005-LLM-교체가능-인터페이스.md) 실측에서 로컬이 유리한 또 하나의 이유다.

### L-3 — 업로드 배치 롤백

잘못 올림 → batch_id로 전량 삭제 → 다시 올림

v1의 미리보기→확정 흐름(`ImportView`)에 더해, **확정 이후에도 되돌릴 수 있는** 경로다.

### S-1 — 인증 도입 시점

**1단계(P1 전용)에는 도입하지 않는다.** 다만 **초판의 근거였던 *"내부망이라 안전하다"* 는 철회한다**(M-1 참조).

새 근거: **감염 대비에는 다른 조치가 더 효과적이다.**

| 조치 | 비용 | 감염 시 효과 |
|---|---|---|
| DB 비밀번호·포트 제한 | ≈ 0 | ⭕ |
| **백업 암호화 + 오프사이트** | 낮음 | ✅ **랜섬웨어 방어의 핵심** |
| 로그인 화면 | 중간 | △ **감염된 PC에선 세션 쿠키도 함께 털린다** |

앞의 두 개는 **1단계에 넣는다.** 로그인 화면만 2단계로 미룬다.

**2단계(아빠 전환) 진입 조건에 인증을 포함한다.** 그 시점에 아빠 데이터가 들어오고 사용자가 2명이 되므로 S-1의 영향이 실재하게 된다.

| 시점 | 인증 |
|---|---|
| 1단계 | ❌ 불필요 (TD-3 유지) |
| **2단계 전환 전** | ✅ **필수** — 세션 기반 로그인, 사용자별 데이터 분리 |

### 완화하지 않고 **수용**하는 위협

> 위험 처리에는 네 가지가 있다 — **완화(mitigate) · 수용(accept) · 전가(transfer) · 회피(avoid)**.
> 나열만 하고 처리를 안 적으면 "잊은 것"과 "의도적으로 안 하는 것"을 구별할 수 없다. MoSCoW의 `Won't`와 같은 논리다.

| # | 위협 | 처리 | 사유 | 재평가 시점 |
|---|---|---|---|---|
| **I-3** | git에 금융파일 커밋 | ✅ **이미 완화됨** | `.gitignore`에 `*.xls*`·`*.csv`·`*.xlsm`·외부템플릿 차단. **검증 완료**(`git check-ignore`) | 새 데이터 파일 유형 추가 시 |
| **R-1** | 변경 이력 없음 (부인) | 🟡 **수용** | 사용자 2명·가족·같이 삶 → **부인 시나리오가 성립하지 않는다.** 단 *실수 추적* 용도는 남아 있어 소프트 삭제(T-1)로 부분 완화 | 사용자가 3명 이상이 되면 |
| **E-1** | 권한 상승 | 🟢 **해당 없음** | **권한 개념 자체가 없다**(1단계 단일 사용자). 상승할 대상이 없음 | **2단계 인증 도입 시 필수 재평가** — 권한이 생기면 이 위협도 생긴다 |
| **D-1** | 거대 파일 업로드 | 🟡 **최소 완화** | 내부망·2인이라 악의적 DoS가 비현실적. 단 **실수로 인한 대용량 업로드**는 가능하므로 크기·행수 제한만 둔다 (§2 D-1) | — |

**E-1은 특히 주의한다.** 지금 "해당 없음"인 이유는 안전해서가 아니라 **권한 체계가 없어서**다. 2단계에서 인증을 넣는 순간 이 위협이 실재하게 되므로, NFR-02 도입 시 **위협모델을 다시 돌린다.**

### RTO를 1시간으로 잡은 이유

복구 자체는 **1초 미만**이다(§4 실측). 병목은 기술이 아니라 **사람이 문제를 알아차리고 조치하는 시간**이다. 서버가 상시 가동이 아니고 실시간성이 없으므로 1시간이면 충분하다.

## 4. 검증 — 실제로 돌렸다 ✅

> **PDF 프로세스의 "Evidence Before Approval" 원칙 적용.** 문서상 주장이 아니라 실행 증빙을 남긴다.
> 사용자 실데이터(`ledger_db_data` 볼륨)는 **접촉하지 않았다** — 격리 컨테이너(포트 5433, 별도 볼륨)에서 수행 후 삭제.

> **재현 가능**: `bash scripts/backup_restore_drill.sh` — 격리 컨테이너에서 전 과정을 자동 수행하고 판정까지 출력한다.
> NFR-01의 *"분기 1회 복구 리허설"* 은 이 스크립트를 돌리는 것으로 충족한다.

### 환경·데이터

```
postgres:16.14 / 격리 컨테이너
v2 설계 스키마 (04_1차설계 §3) + 합성 데이터
  거래 22,047건 · 분류 302(활성 132) · 규칙 8,521  ← 실제 규모 재현
```

### 측정

| 항목 | 실측 |
|---|---|
| 적재 | 0.66초 |
| **`pg_dump -Fc`** | **0.22초 / 1.3MB** |
| **`pg_restore`** | **0.33초** |
| 복구 객체 | 4 테이블 / 7 인덱스 / 4 FK |

### 시나리오 결과

| 위협 | 시나리오 | 결과 |
|---|---|---|
| **L-1** | 컨테이너+볼륨 **완전 삭제** → 신규 기동 → 복구 | ✅ **PASS** — 체크섬 8종(md5 digest 포함) 완전 일치 |
| **L-2** | 동일 데이터 2회 재삽입 | ✅ PASS (수정 후) — 22,047 유지 |
| **L-3** | 200건 업로드 → `batch_id`로 롤백 | ✅ PASS — 22,047 복원 |
| — | `DELETE` 후 `ROLLBACK` | ✅ PASS — 원복 |

### ★ 검증에서 발견한 결함

```
ERROR: there is no unique or exclusion constraint matching the ON CONFLICT specification
```

`external_ref`에 **부분 유니크 인덱스**(`WHERE external_ref IS NOT NULL`)를 걸었더니 `ON CONFLICT (external_ref)`가 매칭되지 않았다. 조건을 명시해야 한다:

```sql
ON CONFLICT (external_ref) WHERE external_ref IS NOT NULL DO NOTHING
```

**FR-28(멱등성)을 "설계했다"로 끝냈다면 운영 중에 터졌을 결함이다.**
→ **교훈: 멱등성은 선언이 아니라 실행으로 확인한다.** Step 7 테스트(`test_migration_idempotent`)에 이 케이스를 고정한다.
