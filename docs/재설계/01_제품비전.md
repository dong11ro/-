## 1. 문제 정의 (Problem Statement)

### v1.0.0의 문제 정의 — 무엇이 틀렸나

기존 [가계부_기능명세서.md](../../가계부_기능명세서.md) 1장:

> "수입·지출을 빠르게 기록하고, 예산을 관리하며, 지출 패턴을 분석한다."

이것은 **문제 서술이 아니라 솔루션 서술**이다. "기록·예산·분석"은 이미 답을 정해놓은 것이라, 이후 "이 기능이 정말 필요한가"를 판정할 기준이 없다. 실제로 회고에 기록된 병목 — *"막대 버킷·예산선·소비/비소비 축을 구현 중 여러 번 되돌아가 재설계"* — 의 뿌리가 여기다. **판단 기준이 없으니 매번 감으로 결정하고, 나중에 뒤집혔다.**

### v2의 문제 정의

> **아빠는** 매달 가계부를 정리할 때, **은행·카드 거래내역을 엑셀로 옮기는 작업을 전부 손으로 한다.** 엑셀은 은행과 연결될 수 없고, 데이터가 쌓일수록 파일이 느려지며, 원하는 시각화를 만들기 어렵다. 그럼에도 대안이 없어 **수년째 이 불편을 감수하며 계속 쓰고 있다.**

부차 문제(P1, 2차 타깃):

> **나는** 토스로 내 계좌를 자동으로 보고 있지만, 최근 받은 아빠 카드로 쓴 지출은 토스가 **구조적으로 볼 수 없다**(본인 인증 계좌만 연동 가능). 그래서 내 실제 소비의 일부가 어떤 도구에도 잡히지 않는다.

### 왜 아빠를 1차 타깃으로 두었나

제품 조사에서 **"불편을 감수하면서도 수년째 계속 쓴다"** 는 최상급 수요 신호이고, **"만들어놨는데 안 쓴다"** 는 최악의 신호다. 지금 두 신호가 각각 아빠와 나에게 붙어 있다. 페인이 강한 쪽을 겨냥한다.

부수 효과: 1차 타깃이 비개발자가 되면서 설계 기준이 *"내가 쓸 수 있는가"* 에서 ***"비개발자가 혼자 쓸 수 있는가"*** 로 바뀐다. 온보딩·오류복구·데이터 신뢰성이 선택이 아니라 필수가 된다.

### 아빠의 페인 — 08-28 전면 수정

| # | 페인 | 실측 근거 | 앱이 이기는가 |
|---|---|---|---|
| **1** | ★ **가맹점명 → 302개 분류코드 매핑** | `Claude Log`에 *"57개 중 18개 매칭"* — **자동 매칭률 약 32%**. 나머지는 AI에 매번 질의하며 수동 배정 | ✅ **핵심 가치** |
| **2** | **영수증 품목 단위 입력** (단가·수량까지 손으로) | `영수증` 시트 구조 | ✅ OCR·파싱 |
| 3 | 데이터 쌓이면 **느려짐** | 17만 행 + 계산체인 10MB | ✅ DB의 본령 |
| 4 | **시각화 한계** | — | ✅ 우위 |

> **08-25판의 "은행과 연결 안 됨 → 전부 수기 입력"은 부정확했다.** 원본 적재는 이미 하고 계신다(계좌 시트에 은행 원문 그대로 보존). **진짜 병목은 입력이 아니라 분류다.**

→ **1번이 이 제품의 존재 이유.** 그리고 베이스라인(32%)이 이미 측정돼 있어 개선을 숫자로 증명할 수 있다.

> ⚠️ **P2는 아직 미검증 페르소나다.** 엑셀 폼 미확보, 실사용 의사 미확인. 리스크 R-1 참조.

## 3. 대체재 분석

경쟁사 기능 나열이 아니라 **"왜 그것을 안 쓰는가 / 그것이 구조적으로 못 하는 것은 무엇인가"** 로 접근한다.

| 대체재 | 이기는 점 | **구조적으로 못 하는 것** |
|---|---|---|
| **토스 등 자동연동 앱** | 트리거(결제 시 푸시), 자동연동, 마찰 0 | **본인 인증 계좌만** 볼 수 있음 → 아빠 카드·타인 명의 자산 불가. 분류 체계를 내 생활에 맞게 바꾸기 어려움 |
| **엑셀 (아빠)** | 스키마 변경 비용 0, 어디서나 열림, 죽지 않음, 완전한 통제 | **은행과 연결 불가**(수기 입력 강제), 파일 성능 한계, 시각화 제작 비용 높음 |
| **v1.0.0 (내가 만든 것)** | 기능은 이미 다 있음 | **트리거가 없음** → 아래 4절 참조 |

### 토스에서 배울 것 — 왜 토스는 쓰이고 v1은 안 쓰였나

행동 = **동기 × 능력 × 트리거** (곱셈이므로 하나라도 0이면 결과는 0)

| | 토스 | v1.0.0 |
|---|---|---|
| 트리거 | 결제하면 **푸시가 옴** | ❌ **없음** |
| 능력 | 자동연동 (사용자가 할 일 0) | 은행 로그인 → 다운로드 → 업로드 |
| 동기 | 불필요 (알아서 해줌) | 강한 의지 필요 |

v1은 "능력" 칸만 6개 화면으로 채웠고, 비어 있던 "트리거" 칸은 건드리지도 않았다.

## 4. v1.0.0 실패 원인 진단

**v1의 실패는 공학 실패가 아니라 제품 설계 실패다.** 코드·아키텍처·파이프라인 추상화는 회고에서 스스로 평가한 대로 잘 되어 있다. 실패한 것은 Step 1이다.

검증 과정에서 세운 가설 두 개가 실제 데이터로 반증되었다. 기록해 둔다 — **틀린 가설을 남겨두는 것이 이 문서의 목적 중 하나다.**

| 가설 | 근거였던 것 | 판정 |
|---|---|---|
| **H-fail-1**: 가용성 문제 (집 밖 접속 불가) 때문에 안 썼다 | 명세서 7.5장 "데스크탑 켜져 있을 때만, 같은 와이파이 내" | ❌ **반증**. 핵심 가치가 "사후 일괄 가져오기"라면 매 결제마다 기록할 필요가 없다. 주 1회 집에서 정리하면 되고, 아빠는 애초에 집에서만 작업한다 |
| **H-fail-2**: 가져오기 마찰(은행 다운로드·초기 분류 노가다) 때문에 중도 포기했다 | 6단계 플로우의 길이 | ❌ **반증**. "한 번도 제대로 안 써봤다" → 중도 포기가 아니라 **시작 자체가 없었다** |
| **H-fail-3**: 트리거 부재 | 위 두 가설이 모두 반증되고 남은 것 | ✅ **채택**. "언제 이걸 여는가"가 명세서 어디에도 없다 |

### 이것이 입력 모델과 인프라 요구사항을 결정한다

| 입력 모델 | 필요한 가용성 | 인프라 |
|---|---|---|
| 실시간 기록 (결제 직후 입력) | 24시간 · 어디서나 | 클라우드 · 외부 접속 · 인증 강화 |
| **사후 일괄 (정기 정리)** ← 채택 | 집에서 · 켜져 있을 때 | **홈서버로 충분** |

→ Step 4(NFR)에서 확정하되, 현재 유력안은 **홈서버 유지**. v1의 인프라 선택은 (재검토 결과) 틀리지 않았다.

## 5. 핵심 가치 제안

> **은행·카드 거래내역을 손대지 않고 내 분류 체계로 가져와, 쌓여도 느려지지 않는 장부로 만든다.**

- 토스가 못 하는 것: 내 계정이 아닌 자산, 내 마음대로인 분류 체계
- 엑셀이 못 하는 것: 은행 연결, 성능, 시각화
- **둘 다 못 하는 교집합이 이 제품의 자리**

## 7. North Star Metric

> 🔄 **08-28 재검토 필요.** 병목이 "입력"이 아니라 "분류"로 확인되었으므로, NSM 후보가 **자동 분류율**로 바뀔 가능성이 크다.
>
> ```
>            (자동으로 올바른 분류코드가 배정된 거래 수)
> 대안 NSM = ───────────────────────────────────────────  × 100
>                        (전체 거래 수)
>
> 현재 베이스라인: 약 32%  (Claude Log 실측: 57개 중 18개)
> 목표: 85%
> ```
>
> **베이스라인이 이미 실측돼 있다는 게 결정적 장점**이다. 개선 폭을 숫자로 증명할 수 있다.
> **Step 3(SRS)에서 아래 원안과 비교해 확정한다.**

### NSM 원안 (08-25): 자동 입력율

```
        (csv/규칙으로 자동 입력된 거래 수)
NSM =  ─────────────────────────────────────  × 100
              (전체 거래 수)

목표: 도입 3개월 내 80%
```

**선정 이유**
- 아빠의 페인 1번(수기 입력)과 직결 — 이 수치가 오르면 페인이 실제로 줄어든다
- 측정이 쉽다 (`transactions.source` 필드로 즉시 계산)
- **개선 방향이 자동으로 도출된다**: 지표를 올리려면 은행 파서 확대 / 자동분류 규칙 품질 / 매핑 프리셋을 개선해야 한다 → 개발 우선순위가 자연히 정렬된다

**한계와 보조지표 (Guardrail)**
NSM만 보면 "가져오기를 아예 안 하면 분모가 0"인 허점이 있다. 따라서 아래를 함께 본다. **단, 의사결정 기준은 NSM 하나다.**

| 보조지표 | 목표 | 왜 필요한가 |
|---|---|---|
| 월간 정리 실행 횟수 | ≥ 2회 | NSM의 분모 방어 (트리거가 작동하는지) |
| 미분류 잔여 건수 | → 0 수렴 | 자동분류가 실제로 학습되는지 |

### 채택하지 않은 후보

| 후보 | 기각 사유 |
|---|---|
| 주간 정리 정착률 | 제품이 좋아서 오르는지 의지로 버티는지 구분 불가. 개선 방향이 모호 |
| 엑셀 이탈 여부 | 궁극 목표로는 적절하나 측정이 수개월 단위로 늦고 거칠어 개발 중 의사결정 기준이 못 됨 → **목표로만 유지, 지표로는 미채택** |

### 주의 — "자금 주체 축" 판정이 뒤집힌 경위

대화 초반에 *"아빠 카드를 다룰 자금 주체 축이 v1에 없다, 단방향 문이라 치명적"* 이라고 판단했으나, 1차 타깃이 아빠로 확정되고 **계정 분리** 모델을 택하면서 판정이 바뀌었다.

| 시나리오 | 자금 주체 축의 성격 |
|---|---|
| 공동 장부 (거래 하나를 둘이 공유) | 집계 전체가 갈라짐 → **단방향 문**, 처음부터 필요 |
| **계정 분리 (각자 장부)** ← 채택 | 내 장부에 필드 1개 + 현금흐름 집계에서 제외 → **양방향 문**, 나중에 추가 가능 |

아빠 관점에서 아빠 카드는 그냥 자기 카드다. 이 축이 필요한 것은 오직 P1의 장부에서다. ~~MVP에서 제외한다.~~

> ### 🔄 08-28 재역전 — MVP 필수로 복귀
>
> 위 추론은 *"아빠는 자기 돈만 본다"* 는 가정 위에 있었다. **틀렸다.**
>
> 아빠 엑셀 실측 결과:
> - `지출소득내역` 시트에 **`동현` 전용 집계 컬럼**
> - 핵심 수식 **`지출-(동현+제외)`** — 가계 지출 계산 시 아들 지출을 분리
> - 계좌 원장에 **`{아들}card-match`** 전용 매칭 컬럼
> - 카드 명세 분류 라벨이 `외식(동현)`, `편의점(동현)` 형태로 **주체가 인코딩**됨
>
> 아빠는 12년 전부터 **한 장부 안에서 여러 주체의 돈을 구분해 집계**해왔다. 이건 나중에 붙일 기능이 아니라 **시스템의 뼈대**다.
>
> **교훈**: 축의 필요성을 사용자 발언이나 논리적 추론으로 판정하려 했던 것이 잘못이었다. **기존 산출물(엑셀)의 집계 수식을 보면 5분 만에 알 수 있는 사실이었다.**
