# 향후 고도화 항목

지금은 단순하게 구현했지만, 나중에 더 똑똑하게/편하게 만들 수 있는 항목을 기록한다.
(우선순위 낮음 — 핵심 기능 안정화 후 진행)

---

## 1. 가맹점 자동분류 고도화 (LLM / ML)

### 현재 구현 (2026-06, C-2)
- **방식**: 사용자 정의 규칙(`merchant_rules`)의 키워드가 가맹점 원문에 **부분 문자열로 포함**되면 해당 카테고리·별칭을 적용.
- **흐름**: 규칙은 비어서 시작 → 사용자가 1회 분류 → "규칙 저장" → 다음부터 자동 (learn-as-you-go).
- **위치**: `backend/app/main.py`의 `_classify()`, 가져오기 미리보기에서 적용.

### 한계
- **내장 지식 없음**: "스타벅스=카페"를 시스템이 원래 알지 못함. 사용자가 가르친 규칙만 안다.
- **오타·표기 변형 못 잡음**: `스타박스`, `STARBUCKS`는 `스타벅스` 키워드로 매칭 안 됨 (글자 그대로 비교).
- **의미 이해 없음**: `메가커피`는 '카페' 글자가 없어 '카페' 키워드 규칙으로 못 잡음.

### 고도화 방향 (쉬운 것 → 어려운 것)
1. **흔한 가맹점 규칙 기본 시딩** (가장 쉬움)
   - 명세서 4.5 예시표 + 한국 인기 가맹점(스타벅스/GS25/CU/배민/쿠팡/올리브영/카카오T 등)을 기본 규칙으로 제공.
   - 카테고리·결제수단 시딩처럼 `seed.py`에 추가하면 됨.
2. **일반 단어 키워드 활용** (구현 불필요, 사용 팁)
   - `카페`·`병원`·`편의점` 같은 공통어를 키워드로 등록 → 해당 단어 포함 가맹점 일괄 분류.
3. **ML 분류기**
   - 특성: 가맹점명·금액·요일·시간 등 → 카테고리 예측.
   - 학습 데이터: 사용자가 이미 분류한 거래(라벨)를 그대로 활용 (개인화).
4. **LLM 분류**
   - 가맹점명을 LLM에 보내 "이 가게는 어떤 카테고리?"를 분류 → 퍼지/의미 이해 가능 (메가커피 → 카페 등).
   - 로컬 LLM(Ollama) 활용 시 프라이버시·비용 유리.
5. **외부 가맹점 DB / 사업자번호 매칭**
   - 표준 업종분류와 연결.

### 적용 시 고려사항
- **프라이버시**: 외부(LLM/API)로 보낼 땐 최소 정보만(가맹점명). 계좌번호·잔액·금액은 제외. 로컬 LLM이면 더 안전.
- **폴백**: 자동 분류 실패 시 기존 키워드 규칙 → 수동 분류 순으로 폴백.
- **사용자 확인**: 자동 결과는 "추천"으로 표시하고 사용자가 확정 (오분류 방지).
- **규칙과 병행**: ML/LLM이 추천한 분류를 사용자가 확정하면 규칙으로도 저장 → 다음부턴 규칙이 먼저 처리(빠르고 무료).

## 2. 투자/자산 손익 추적

### 현재 (가계부 = 현금흐름)
- 가계부는 **통장에 들어오고 나간 거래**만 기록한다.
- 투자 입금 = 비소비(투자)로 통장에서 나감 → 현금흐름에 잡힘.
- 매도해서 돈이 돌아오면 = 수입 → **실현 손익**이 자연히 반영됨.

### 한계
- **평가 손익**(안 팔았는데 오르내린 것)은 "거래"가 아니라 "시세"라 가계부가 못 잡는다.
- 즉 "지금 내 주식이 얼마인지"는 현재 가계부 범위 밖.

### 고도화 방향
- **자산/포트폴리오 추적** 별도 도입: 보유 종목·수량·평가액(시세)을 주기적으로 기록 또는 증권사/시세 API 연동.
- 평가 손익·수익률·자산 배분(안전/위험) 시각화.
- 가계부(현금흐름)와 자산추적(평가액)은 데이터 성격이 달라 별도 모듈로.
- 로컬 자동화(시세 크롤링/LLM)와 엮을 수 있음.

### 배경 · 왜 MCP인가
- 이 앱은 **AI를 내장하지 않는다.** MCP로 "도구"만 노출하고, 사용자가 **자기 Claude(Desktop/Code)를 연결**해서 쓴다. → 앱은 LLM 비용·API 키·챗 UI를 하나도 안 떠안는다.
- **역할 분담**: 앱 = 데이터·계산·저장 / AI = 이해·판단·서사.
- **사용 리듬 전제**: 사용자는 매일 안 쓴다. **주 1회 / 월 1회 몰아서** 기록·검토한다. → 배치 "가져오기" + 회고형 "분석"에 최적화한다 (실시간 예측은 부차).

### 3-1. AI 만능 가져오기 (핵심 기능)

**현재 구현**
- 은행 양식별 파서를 **손으로 하드코딩** (`importer.py`의 `parse_simple`, `parse_kb`), `PARSERS` dict로 분기.
- 흐름: 파일 업로드 → `parse` → 가맹점규칙 자동분류 + 지문 중복감지 → 미리보기 → commit.

**한계**
- **양식마다 파서를 새로 짜야 함.** 우리은행·토스·카드사가 추가될 때마다 개발 노가다. 사용자의 임의 파일은 영원히 다 못 커버.
- **의미 뉘앙스를 못 읽음.** 예: KB 파일의 `구분` 열이 `취소`/`취소된거래`인 행을, 지금 `parse_kb`는 그 열을 안 읽어 **취소 거래까지 진짜 지출·수입으로 저장** → 통계 오염. "오픈뱅킹출금 토스페이충전"(충전=이체)도 소비로 잡힘.

**고도화 방향**
- **파서를 LLM으로 대체.** 사용자의 Claude가 어떤 CSV/XLS든 직접 읽어 **표준행**으로 변환해 앱에 넘긴다. 앱은 파일을 안 받고 JSON 행만 받으므로 도구가 단순해진다.
- 표준행에 Claude의 **판단 필드**를 넉넉히:
  ```
  { date, type, amount, merchant, memo,
    category?,          // Claude 제안 (규칙에 없어도)
    payment_method?,    // 적요("체크카드"/"오픈뱅킹") 등에서 유추
    is_transfer?,       // 충전·이체 등 비소비 여부
    skip_reason? }      // "cancelled"(취소거래) 등 → 제외 후보
  ```
- 흐름: `preview_import(rows)` → 자동분류·중복·판단을 붙여 **"이렇게 들어갈 거야"** 반환(저장 X) → 사용자 확인 → `commit_import(rows)`. 기존 지문 중복감지·규칙 저장 로직 그대로 재사용.
- **애매한 건(취소·충전·미분류)은 자동 처리하되 미리보기에서 전부 보여주고 확인받는다.** (한 방에 안 넣음)

### 3-2. 대시보드 너머 분석 · 조언

**현재 구현**
- 대시보드가 **미리 정한 질문**에 답: 월 총액·현금흐름, 대분류 지출 랭킹, 가맹점 TOP(금액순), 지난달 대비 증감.

**한계**
- 고정 차트라 **미리 못 박아둔 질문·판단·서사**는 못 한다.

**고도화 방향 — AI만 할 수 있는 7가지**

| # | 버킷 | 예시 | 대시보드가 못 하는 이유 |
|---|------|------|----------------------|
| 1 | 긴 꼬리 질문 | "커피값이 점심값보다 많던 날?" | 질문 무한 → 차트로 못 박음 |
| 2 | 새는 돈(소액·고빈도) | "편의점 300회 × 2천 = 62만" | TOP이 금액순이라 소액 습관 안 보임 |
| 3 | 구독·정기결제 탐지 | "매달 반복 = 넷플릭스·헬스장…" | `is_fixed`가 수동. 반복을 자동 발견 |
| 4 | 이상 탐지 + 서사 | "카페 3만→12만 급증, 첫 등장 5곳" | 가맹점 단위 이상·신규·소멸 없음 |
| 5 | 예측(가져온 시점 기준) | "이대로면 월말 예산 초과 예상" | 대시보드는 전부 과거 회고 |
| 6 | 행동 코칭 | "줄일 지출 3개", "충동구매 의심" | 판단·추론 필요 |
| 7 | 서사형 리포트 | "이번 달 한 문단 요약(가족 공유)" | 숫자 나열이 아닌 맥락 있는 글 |

**설계 원칙**
- **엔드포인트 20개로 만들지 않는다** (그럼 또 고정 차트). **유연한 읽기 도구 몇 개**만 열고 분석·판단은 Claude에게 맡긴다. 버킷 1·2·4·6·7은 이 방식으로 사실상 공짜. 3·5(구독탐지·예측)만 무거우면 전용 도구를 나중에 얹는다.

### 도구 표면 (초안)

| 도구 | 종류 | 역할 |
|------|------|------|
| `list_categories` | 읽기 | Claude가 유효 카테고리 파악 |
| `search_transactions(필터)` | 읽기 | 분석·질문의 만능 소스 (기간·카테고리·가맹점·금액·태그) |
| `get_budget_status` | 읽기 | 예산 대비 현황 |
| `preview_import(rows)` | 읽기(계산) | 분류·중복·판단 붙여 반환, 저장 X |
| `commit_import(rows)` | **쓰기** | 실제 저장 (확인 후) |

---

### 구현 방식
- **독립 FastMCP 서버 권장.** `preview_import`처럼 여러 로직을 묶은 맞춤 도구가 필요해, 기존 REST를 1:1 자동 노출하는 방식(`fastapi-mcp`)보다 손수 설계가 맞다.
- `docker-compose.yml`에 `mcp` 서비스 추가(백엔드 코드/DB 재사용). HTTP transport로 노출 → `claude mcp add --transport http ledger http://<host>:<port>/mcp` 로 연결.

---

### 고려사항
- **프라이버시**: LAN 로컬. 파일은 Claude가 읽고 **표준행만** 앱에 전달(계좌번호·잔액은 안 보냄). 외부 서버 전송 없음.
- **안전장치**: 쓰기 도구(`commit_import`)는 **preview 확인 후에만**. 대량 저장 실수 방지.
- **사용 리듬**: 주1/월1 배치 → **가져오기 + 회고 리포트** 중심. 예측(버킷5)은 데이터 신선도 낮으면 신뢰도 단서를 붙인다.
- **시각 보존(별도 항목 후보)**: 버킷 6의 "밤 시간대" 분석은 현재 불가 — `importer._to_date`가 시각을 버림. 시간대 분석하려면 스키마에 시각 보존 필요.
